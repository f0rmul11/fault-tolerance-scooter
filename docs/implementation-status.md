В последующем рефакторинге выделены узкие application services. В Pricing

домена, application service сохраняет их через flusher одной транзакцией с
состоянием. Проверки и повторное развёртывание пройдены (docs/verification.md).


Последнее уточнение: доменные изменения и формирование событий выполняются из
use case с собственными Input. Application services получают готовые сущности.
Profile разделяет Save и SaveSubscriptions, общая транзакция находится в сервисе.
В Profile/Scooter версии сравниваются только в UPDATE, включая expected_version
клиента и версию прочитанного снимка. Unit/race/vet, отдельные проверки PostgreSQL
и итоговый HTTP-прогон после повторного развёртывания пройдены.

Pricing не содержит application/service, поля services в App и initServices.
Reserve вызывает storage.Create, start/complete/cancel — storage.Save после
доменных методов непосредственно загруженного Trip, без разыменования и копии.

Scooter предоставляет две отдельные операции обновления: availability для
is_active и owner для названия юридического лица. Заряд и общий UpdateScooter
удалены из контракта, модели, схемы и seed. Rental проверяет is_active при новой
брони; существующая аренда продолжает работать после отключения самоката.
Контракты меняются без обратной совместимости: reserved для удалённого поля нет.
Buf-код владельца, Rental и gateway, а также XO перегенерированы инструментами.
Проверены две ручки, SQL CAS при конкурентных изменениях и полный цикл аренды
через HTTP/Kafka; подробности — docs/verification.md.

## Инструменты домашнего задания модуля 3 — 1 ноября 2026

Реализованы `fault api-gateway scooter --method GetScooter` с процентом
Unavailable либо постоянной задержкой, foreground duration/Ctrl+C/--clear,
`load` через закреплённый Framer и `logs api-gateway --outgoing`.
Прокси применяется штатными up/deploy; другие методы и Rental → Scooter
не затрагиваются. Gateway передаёт request_id и поддерживает адресный override,
сохраняя остальные зависимости. Retry, backoff и budget не реализованы.
Домашка module-3 сохраняет постановку, SLO и семантику бюджета, но использует
явные fault/load-команды и JSON-тело в параметре --data вместо режимов homework.

Выполнены `make cli`, `go test -race ./...` и `go vet ./...` в scooterctl и
api-gateway с GOWORK=off. Отдельно запущен TestFramerSendsRequestDeadline с
реальным адаптированным Framer: gRPC-сервер получает deadline 100 мс.

На локальном k3s проверены базовые ответы, 5/40/100% Unavailable, задержка 500 мс,
внешний deadline 100 мс (ответ примерно за 103–104 мс), исходящие логи с request_id,
изоляция ListScooters и прямого Scooter.GetScooter, снятие по duration и Ctrl+C,
--clear после SIGKILL и частичный отчёт при прерывании load. Внешняя отмена может
попасть в phout как grpc_4 или HTTP/2 rst_8; оба учитываются как ошибки.
Прогоны короткие (до 1000 запросов), это проверка инструментария, а не выполнение
ученического SLO на 10-минутной нагрузке. Сбои после проверки сняты, данные не
сбрасывались. Решение ученика для retry/budget в эти проверки не входит.


### Проверка инструментов module-3 — 1 ноября 2026

Практическое прохождение ДЗ выявило два дефекта наблюдения. Для `logs -f`
отключён унаследованный 10-секундный HTTP timeout только на потоковом клиенте;
обычные запросы остаются ограниченными. Добавлен тест настоящего HTTP-потока.
Интервал выгрузки исходящих логов уменьшен до 100 мс, в ДЗ уточнены завершение

на локальном k3s. Код ученического решения и подробные отчёты хранятся только
локально и в репозиторий не входят. Retry, backoff и budget оставлены ученикам.


### Упрощение module-3 — 3 ноября 2026

Домашка состоит из двух последовательных экспериментов: временные 5% ошибок
с пятиминутной нагрузкой до/после решения и полный отказ с подсчётом попыток
до/после добавления бюджета. Добавлено объяснение ёмкости и пополнения бюджета.
Сдача — PR с решением в API Gateway. `access` выводит gRPC и admin-адреса
из конфигурации портов.

Инструменты проверены на локальном k3s и через race/vet. Частное ученическое
решение и подробные отчёты остаются только локально; в стартовые сервисы
retry/budget не добавлены.

### Методички и единая модель бюджета — 3 ноября 2026

В homeworks/module-3/manual добавлены методички по retry/backoff/budget/pushback
и идемпотентности с версией списка броней. Примеры привязаны к коду лекционного
HotelFlow. Требования ДЗ приведены к тому же throttler: списание за ошибку,
запрет повторов на половине запаса, пополнение успехами. Прежнее ожидание
620 попыток для ёмкости 20 относилось к другой модели и больше не применяется.

Retry/budget в стартовые сервисы не добавлены; приватное решение и отчёты
проверки остаются только локально.

### Самостоятельный выбор политики бюджета — 3 ноября 2026

В module-3 ученик выбирает допустимую долю дополнительных попыток на полном
отказе, рассчитывает ёмкость и объясняет ratio через восстановление успехами.
Фиксированная обязательная конфигурация 20/0.1 заменена расчётом политики;
пороговый алгоритм HotelFlow сохранён. По 600 запросам генератора и исходящим
логам вычисляются попытки, повторы и их доля. Результат сопоставляется с верхней
границей; точное равенство не требуется. Сдача остаётся PR с решением и
комментариями конфигурации, без отдельного отчёта.


## Основа домашнего задания модуля 4 — 4 ноября 2026

Добавлена готовая бизнес-цепочка API Gateway → Profile.GetDiscount →
Pricing.GetCompletedTripsCount. Profile проверяет локального пользователя,
Pricing считает только COMPLETED в своей БД; скидки 0/10/20% относятся
к отображению в личном кабинете и не меняют расчёты поездок.
Контракты и внешние клиенты сгенерированы Buf. Для Gateway использован
штатный offline target с закреплёнными импортами: BSR вернул HTTP 403.

Стартовые сервисы не содержат решения задач по CB, timeout, fallback и /metrics.
Домашка оставляет выбор реализации ученику, содержит отдельные критерии для
пяти заданий (включая отдельный блок вопросов о CB) и данные 0/12/55,
которые автоматически создаются миграциями сервисов.
Повторные запросы и пробы Kubernetes в задания модуля 4 не входят.

scooterctl fault поддерживает Profile → Pricing.GetCompletedTripsCount:
Unavailable, фиксированную задержку, вероятность и duration/Ctrl+C/clear.
Связь api-gateway → Scooter.GetScooter сохранена и проверена отдельно.
RPC-прокси ограничивает воздействие точным методом; SERVICE_TARGETS в Profile
направляет вызовы через него. access показывает admin/gRPC адреса сервисов,
logs profile --outgoing позволяет наблюдать попытки в общем прокси.

Проверены race/vet в scooterctl, profile, pricing и api-gateway; настоящая
генерация, сборка образов, deploy и SQL fixtures. На стартовом коде проверены
0/12/55 поездок, HTTP 503 скидки при сохранении HTTP 200 обычного профиля,
отмена двухсекундной инъекции клиентским deadline 100ms (p99 104ms).
При инъекции старой связи Scooter возвращает 503, скидка остаётся доступной.

Независимый ревизор реализовал ученическое решение в отдельной локальной копии.
Три реальных прогона по 10 минут при 2 RPS: каждый 1200/1200 успешных ответов.
Клиентские p99: 10ms без сбоя, 9ms при полном Unavailable, 189ms при задержке 2s.
На полном отказе в зависимость ушло 122 попытки, на задержке — 120;
остальные обращения отсечены CB, клиент получил явную деградацию.
Эти результаты относятся к проверочному ученическому решению, а не к starter.
