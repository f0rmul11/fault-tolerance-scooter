## 1. «После релиза пропадают тарифы»

> 💬 **Поддержка:** «После обновления пользователи видят пустой список тарифов. Через полминуты всё появляется. При этом API отвечает HTTP 200».

Исторически тарифы хранятся в [`services/pricing/tariffs.json`](../../services/pricing/tariffs.json). Pricing загружает их в память около 30 секунд, но сервер запускается раньше. Во время rolling update новый pod получает запросы до готовности справочника.

**Задача:** найдите загрузку данных и исправьте readiness. Проверяемая ручка — `GET /v1/pricing/tariffs`, RPC — `PricingService/ListTariffs`.

### 🔧 Технические ожидания

| Состояние справочника | `/healthcheck/ready` | Поведение pod |
| --- | --- | --- |
| Загружается | `503` | Работает, но не готов к обычному трафику |
| Успешно загружен | `200`, если остальные проверки успешны | Может обслуживать запросы |
| Ошибка чтения файла | `503` | Остаётся неготовым; ошибка чтения видна в логах Pricing |

Прогрев не должен вызывать перезапуски. Готовые реплики продолжают обслуживать пользователей.

> 💡 Готовность определяется результатом загрузки. Увеличение `initialDelaySeconds` или ожидание фиксированных 30 секунд не исправляют проверку.

### 🧪 Как убедиться, что исправление работает

```sh
./bin/scooterctl homework module-2 run readiness
```

Сценарий запускает запросы, выполняет rolling update и показывает готовность pod, ответы с тарифами и число рестартов. Отдельно проверяет старт с ошибкой чтения файла.

**До исправления:** новый pod принимает запросы слишком рано, часть ответов содержит пустой справочник.

**После исправления:**

- [ ] Pod становится готовым только после загрузки данных; перезапусков из-за прогрева нет.
- [ ] Во время rollout нет пустых успешных ответов и ошибок из-за непрогретой реплики.
- [ ] При ошибке файла pod остаётся неготовым, даже когда время прогрева прошло.

После изменения кода пересоберите Pricing и повторите проверку:

```sh
./bin/scooterctl build pricing
./bin/scooterctl deploy pricing
./bin/scooterctl homework module-2 run readiness
```

**Сравните строку `ТРАФИК`:** до исправления есть пустые HTTP 200; после — все ответы с тарифами, пустых ответов и ошибок — 0. Проверка может идти несколько минут: реплики прогреваются по очереди.

**Вопрос:** почему трафиком здесь управляет readiness? Чем отличаются задачи startup и liveness?

## 2. «Можно удалить `terminated`?»

> 💬 **Коллега на ревью:** «В `App` есть `terminated int32`. Зачем он, если Kubernetes и так умеет останавливать pod?»

Изучите [App](../../services/pricing/internal/app.go), [инициализацию](../../services/pricing/internal/init.go) и [Closer](../../services/pricing/internal/pkg/closer/closer.go). Ответьте:

1. Что означает флаг и чем отличается от `started`?
2. Кто его изменяет и читает? Почему доступ из разных горутин должен быть безопасным?
3. Как обрабатываются `SIGTERM` и `SIGINT`? Почему нельзя обработать `SIGKILL`?
4. Что флаг делает при graceful shutdown, а кто завершает уже принятые запросы?
5. Гарантирует ли порядок регистрации функций в `Closer` порядок выполнения?

### 🔧 Технические ожидания

> 📌 **Флаг сохраняем.** После начала завершения readiness становится неуспешной. Liveness не должна сообщать о поломке только из-за штатной остановки. Поздняя загрузка данных или `uncordon` не возвращают завершающийся процесс в готовность.

### 🧪 Как убедиться, что код это обеспечивает

```sh
./bin/scooterctl homework module-2 run shutdown
```

Сценарий выбирает pod, инициирует штатное завершение и выводит журнал остановки и результаты проверок готовности.

Найдите в выводе получение сигнала, начало завершения, изменение readiness и остановку серверов. Объясните порядок событий по коду. Проверьте, что liveness не стала неуспешной только из-за shutdown. Сам статус `Terminating` не доказывает правильную работу флага.

**Результат:** короткие ответы со ссылками на код и подтверждённое поведение флага. Переписывать весь graceful shutdown не требуется.

## 3. «Выведите один pod из трафика для диагностики»

> 💬 **Дежурный:** «Один экземпляр Pricing тормозит. Нужно убрать его из обслуживания, исследовать и вернуть. Перезапускать нельзя — потеряем состояние».

Добавьте на административный HTTP-сервер:

| Операция | Что должна делать |
| --- | --- |
| `POST /cordon` | Устанавливать ручной запрет участия **этого экземпляра** в трафике через readiness |
| `POST /uncordon` | Снимать ручной запрет, сохраняя остальные проверки готовности |

### 🔧 Технические ожидания

- При `cordon` readiness возвращает `503`; процесс, admin и liveness продолжают работать.
- `uncordon` возвращает готовность только исправному экземпляру. Он не отменяет прогрев, ошибку загрузки или shutdown.
- Повторные вызовы безопасны; операции не затрагивают другие pod и не вызывают перезапуск.

> 💡 Cordon здесь — обратимый запрет на приём обычного трафика. Он нужен для диагностики без удаления процесса. Команда `kubectl cordon` управляет размещением pod на узле и эту задачу не решает.

### 🧪 Как убедиться, что код работает правильно

```sh
./bin/scooterctl homework module-2 run cordon
```

У Pricing **три реплики**. После добавления ручек выполните `build pricing` и `deploy pricing`.

В отдельном терминале наблюдайте выбранный экземпляр:

```sh
./bin/scooterctl status pricing --watch
```

Сценарий выбирает один pod, вызывает `/cordon` и `/uncordon` и проверяет новые соединения. В статусе меняются `READY` и проверка `cordon`; имя pod и число рестартов сохраняются. Остальные реплики остаются готовыми.

| Шаг проверки | Ожидаемый результат |
| --- | --- |
| Вызван `/cordon` | Readiness — `503`; после обновления маршрутизации новые соединения идут к другим готовым репликам |
| Вызван `/uncordon` у исправного pod | Readiness — `200`; экземпляр снова может получать новые соединения |
| Завершилась загрузка после `/cordon` | Ручной запрет сохраняется, pod остаётся неготовым |
| Вызван `/uncordon` при ошибке загрузки или shutdown | Pod не возвращается в готовность |
| Цикл cordon → uncordon без shutdown | UID pod и число рестартов не изменились; admin доступен, другие реплики не затронуты |

> 🔎 Readiness не закрывает уже открытые gRPC-соединения. Сценарий проверяет маршрутизацию на новых соединениях; продолжающий работать старый канал сам по себе не означает ошибку.

## ✅ Критерии успеха и сдача

- [ ] **Для пользователя:** rollout не приводит к пустым тарифам или ошибкам из-за непрогретой реплики.

- [ ] **Для команды:** роль `terminated` объяснена по коду; проверки готовности учитывают одновременно данные, ручной запрет и завершение.
