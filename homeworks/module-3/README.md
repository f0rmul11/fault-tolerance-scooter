# 🛴 Модуль 3. «Карточка иногда не открывается»

📚 Под рукой: [ретраи, backoff, бюджет и pushback](manual/retries.md) · [идемпотентность и версии](manual/idempotency.md).

## 🎭 Контекст истории

Компания **ScooterFlow** развивает сервис аренды самокатов. Пользователь выбирает самокат на карте, открывает карточку и решает, бронировать ли поездку.

За карточкой API Gateway обращается к Scooter по gRPC:

```text
Пользователь → API Gateway → Scooter.GetScooter
```

Чтение карточки не изменяет данные.

## 🧰 Чем пользоваться

Все команды выполняются из корня репозитория. Подготовка окружения — в [основном README](../../README.md).

```sh
make cli
./bin/scooterctl doctor
./bin/scooterctl up --timeout 15m
./bin/scooterctl status api-gateway
./bin/scooterctl access
```

Дождитесь готовности Gateway. Для экспериментов используем:

- **`fault`** — задаёт процент ошибок на связи `API Gateway → Scooter.GetScooter`, не затрагивая остальные вызовы.
- **`load`** — запускает встроенный gRPC Framer и выводит итоговую статистику. При первом запуске нужны Go, Git и доступ к сети для установки генератора.
- **`logs --outgoing`** — сохраняет попытки обращения в Scooter. Понадобится во втором задании.

В командах нагрузки ниже указан UUID самоката из стартовых данных. Если вы меняли данные, выберите существующий самокат через Swagger по адресу из `access` и замените `scooter_id` в параметре `--data`.

## 🚨 Что случилось в проде

> 💬 **Поддержка:** «Иногда карточка самоката не открывается. Через мгновение всё снова работает. Пользователи жалуются на ошибки».

Gateway получает от Scooter временные ошибки `Unavailable`. Нужно уменьшить их влияние на пользователя и сохранить **p99 времени ответа ≤ 300 мс**. Пустая или выдуманная карточка вместо ошибки не подходит.

## 🔹 Задание 1 — Устранение влияния временных сбоев

### 1. Убедитесь, что проблема есть

В **терминале 1** включите временные ошибки:

```sh
./bin/scooterctl fault api-gateway scooter \
  --method GetScooter \
  --unavailable --percent 5 --duration 15m
```

Дождитесь `ACTIVE`. Теперь случайные **5% обращений** на выбранной связи получают `Unavailable` до обработки в Scooter.

В **терминале 2** запустите нагрузку:

```sh
./bin/scooterctl load \
  --addr 127.0.0.1:19090 \
  --method api_gateway.scooter.v1.ScooterService/GetScooter \
  --data '{"scooter_id":"3499a1fb-030c-47a8-bcd2-0ce8304d6a22"}' \
  --rps 20 --duration 5m --request-timeout 3s
```

Это **6 000 пользовательских запросов за 5 минут**. Если меняли порты, подставьте gRPC-адрес Gateway из `access`.

Дождитесь завершения. В строке **«ИТОГО»** посмотрите число и процент ошибок, ниже — p95/p99. До исправления ожидаем около **5% ошибок**, то есть примерно 300 из 6 000. Точное число случайно.

### 2. Подумайте, как помочь пользователю

- Какой механизм из урока подходит для временного сбоя?
- Как сделать так, чтобы отдельная ошибка Scooter не становилась ошибкой пользователя?
- Как ограничить время ожидания, чтобы решение не нарушало цель 300 мс?

Выберите и реализуйте решение на стороне **исходящего клиента API Gateway → Scooter.GetScooter**. Настройки должны задаваться через конфигурацию. Бизнес-логику Scooter менять не нужно.

Начать можно с [инициализации gRPC-клиентов](../../services/api-gateway/internal/init.go). Полное имя исходящего метода — `/scooter.scooter.v1.ScooterService/GetScooter`; оно отличается от входного RPC Gateway в команде генератора.

### 3. Проверьте результат на том же сбое

Остановите `fault` через **Ctrl+C в терминале 1** и дождитесь «Правило снято». Соберите и разверните решение:

```sh
./bin/scooterctl build api-gateway --timeout 10m
./bin/scooterctl deploy api-gateway --timeout 10m
./bin/scooterctl status api-gateway
```

Снова выполните **те же команды `fault` и `load` из шага 1**: 5% ошибок, 20 RPS, 5 минут.

**Цель контрольного прогона: 6 000 успешных ответов, 0 ошибок у генератора, p99 ≤ 300 мс.** При этом искусственные ошибки на связи всё ещё включены — теперь ваше решение скрывает их от пользователя.

Отказы случайны: ограниченное число попыток не гарантирует ноль ошибок в каждом прогоне. Если ошибки остались, разберите причины и настройки, а не просто перезапускайте нагрузку до удачного результата.

## 🔹 Задание 2 — Спасение утопающего

> 💬 **Дежурный:** «Временные сбои мы переживаем лучше. Но теперь Scooter полностью недоступен, а наше решение отправляет в него ещё больше запросов».

### 1. Посмотрите, что делают ретраи при полном отказе

Остановите предыдущий `fault`. В **терминале 1** включите 100% ошибок:

```sh
./bin/scooterctl fault api-gateway scooter \
  --method GetScooter \
  --unavailable --percent 100 --duration 15m
```

Дождитесь `ACTIVE`. Ваше решение с ретраями остаётся включённым.

В **терминале 3**, до запуска нагрузки, начните сохранять попытки:

```sh
./bin/scooterctl logs api-gateway --outgoing -f --tail 0 \
  | tee /tmp/scooter-without-budget.log
```

В **терминале 2** отправьте 600 запросов:

```sh
./bin/scooterctl load \
  --addr 127.0.0.1:19090 \
  --method api_gateway.scooter.v1.ScooterService/GetScooter \
  --data '{"scooter_id":"3499a1fb-030c-47a8-bcd2-0ce8304d6a22"}' \
  --rps 20 --duration 30s --request-timeout 3s
```

Генератор получит **600 ошибок — 100%**. Но сколько обращений ушло в зависимость?

После завершения нагрузки подождите две секунды, остановите **только просмотр логов в терминале 3** через Ctrl+C и посчитайте:

```sh
grep -c '"method"' /tmp/scooter-without-budget.log
```

Одна JSON-строка с `method` — одна попытка, включая искусственно отклонённую. Например, при **трёх попытках на запрос** и достаточном времени на них получится **1 800 обращений: 600 первых + 1 200 retry**. При другом лимите число будет другим.

Мы не помогли ни одному пользователю, но увеличили нагрузку на проблемную зависимость. **Как ограничить дополнительную работу всего потока, а не только одного запроса?**

### 📌 Что такое retry-бюджет

Retry-бюджет — это **ограничение дополнительной нагрузки**, которую мы разрешаем создавать повторными попытками, чтобы не перегружать зависимость.

❗ Мы должны уйти от «Сколько retry мы хотим делать для каждого запроса?» и прийти к «Какую дополнительную нагрузку зависимость может выдержать, когда она деградирует?».

Что же означает наша конфигурация?

```yaml
throttle_max_tokens: 20   # начальный и максимальный запас токенов
throttle_token_ratio: 0.1 # сколько токенов возвращает успешный RPC
```

В алгоритме из лекции общий счётчик начинается с **20 токенов**:

- Каждая учитываемая ошибка списывает **1 токен**, включая ошибку последней попытки. Ниже нуля запас не опускается.
- Каждый успешный RPC возвращает **0,1 токена**, максимум до 20.
- После ошибки повтор разрешён, только если осталось **больше половины запаса**, то есть больше 10. Лимит попыток и deadline тоже продолжают действовать.
- Первые попытки проходят всегда. Их успехи позволяют восстановить запас после аварии. Время само по себе токены не пополняет.

❗ Токен списывается **за ошибку**, а не за отправленный retry. Так мы прекращаем повторы, когда ошибок становится слишком много, и возвращаем их по мере восстановления зависимости.

Переведём в термины нагрузки на примере:

Сервис получает **200 успешных ответов зависимости в секунду**. При `throttle_token_ratio = 0.1` это даёт `200 × 0.1 = 20 токенов/сек` пополнения, пока счётчик не достиг максимума.

Такой поток успехов может компенсировать **20 учитываемых ошибок в секунду**. Если ошибок больше, запас уменьшается и достигает порога запрета повторов.

```text
скорость пополнения = успешные RPC в секунду × throttle_token_ratio
```

❗ Это не гарантированный лимит «20 retry/сек»: ошибки списывают токены даже тогда, когда следующей попытки уже не будет. При полном отказе успехов нет — запас только уменьшается.

---

#### Как выбирать `throttle_token_ratio`?

Сколько успешных вызовов должно компенсировать одну ошибку?

- `0.1` — десять успехов компенсируют одну ошибку.
- `0.2` — пять успехов компенсируют одну ошибку.

❗ Пример: хотим, чтобы **200 успешных RPC компенсировали 40 ошибок**.

`40 / 200 = 0.2` → `throttle_token_ratio: 0.2`.

Больший ratio быстрее восстанавливает запас и возвращает повторы. Меньший — требует больше успешных ответов. Выбирайте его по тому, насколько уверенно зависимость должна восстановиться, прежде чем снова получать дополнительную нагрузку.

---

#### Как выбирать `throttle_max_tokens`?

Это не про RPS. Это про то, **сколько ошибок мы готовы пережить из полного запаса, прежде чем сказать повторам «стоп»**.

При ёмкости 20 порог равен 10. Первые девять ошибок оставляют запас выше порога: 19, 18, …, 11. Десятая ошибка уменьшает его до 10 — новый повтор уже запрещён.

Большая ёмкость позволяет дольше терпеть ошибки, но увеличивает возможный всплеск повторов и время восстановления пустого счётчика. Маленькая быстрее подавляет повторы.

❗ Ёмкость 20 не означает «20 разрешённых retry» или «20 секунд работы». В нашем алгоритме важно учитывать **порог на половине запаса** и списание за каждую учитываемую ошибку.

---

В этом задании вам предстоит **проанализировать и выбрать разумный бюджет повторов**. Примеры кода из лекции — в [методичке](manual/retries.md#4-бюджетирование-ограничить-весь-поток).

### 2. Выберите и реализуйте политику бюджета

Определите, какую **долю дополнительных попыток относительно 600 исходных запросов** вы готовы допустить при полном отказе. Выберите предел меньше 100%, допускающий хотя бы один повтор на 600 запросов, — например, 1–5% — и объясните, почему такая дополнительная нагрузка приемлема.

До запуска нагрузки рассчитайте настройки. Для простоты используйте чётную ёмкость `M = throttle_max_tokens`:

```text
N = 600 — исходные запросы
B = floor(N × допустимый процент / 100) — максимум дополнительных попыток
M = 2 × (B + 1) — ёмкость счётчика
```

`floor` означает округление вниз до целого числа.

Почему так: при полном запасе только первые **`M / 2 − 1` ошибок** оставляют счётчик выше порога. Каждая может разрешить не более одного retry. Поэтому эта ёмкость даёт **не более `B` повторов** за наш прогон без успехов. Это граница для 600 запросов с полным начальным запасом, а не постоянная процентная квота на любой интервал.

**Пример расчёта:** предел 2% → `600 × 0.02 = 12` повторов → ёмкость `2 × (12 + 1) = 26` → не более **612 попыток**. Это пример, свою политику выберите и обоснуйте сами.

Отдельно выберите `throttle_token_ratio`: сколько успешных RPC должно компенсировать одну ошибку? Например, 10 успехов → ratio `1 / 10 = 0.1`. При 100% ошибок пополнения нет, поэтому влияние этого параметра в таком прогоне не видно.

Реализуйте бюджет с выбранными настройками. Он должен быть **общим для запросов и горутин**, а списание за ошибку и проверка порога — атомарными; пополнение тоже защищено от гонок. Не создавайте новый бюджет на каждый запрос или запуск генератора.

В комментариях к конфигурации кратко укажите **допустимый процент, расчёт ёмкости и причину выбора ratio**. Бюджет работает вместе с лимитом попыток, backoff и общим deadline.

Остановите сбой и разверните изменения командами `build` и `deploy` из задания 1. Новый процесс начнёт с полного запаса.

### 3. Сравните число попыток до и после

Снова включите **100% ошибок** командой из шага 1. В терминале 3 начните новый файл логов:

```sh
./bin/scooterctl logs api-gateway --outgoing -f --tail 0 \
  | tee /tmp/scooter-with-budget.log
```

Повторите ту же **30-секундную нагрузку на 600 запросов**. В отчёте генератора убедитесь, что завершились все **600 запросов**, ошибки — **100%**. После этого подождите две секунды, остановите просмотр логов и посчитайте попытки и долю повторов:

```sh
awk '/"method"/ { attempts++ }
END {
  printf "Попыток: %d\nПовторов: %d\nДоля повторов: %.2f%%\n", \
    attempts, attempts - 600, (attempts - 600) / 600 * 100
}' /tmp/scooter-with-budget.log
```

Сопоставьте результат со своим расчётом:

- **Повторы = попытки − 600.** Их должно быть не больше выбранного `B`.
- **Доля повторов = повторы / 600 × 100%.** Она должна укладываться в выбранный процент.
- Например, для политики из примера ожидаем **не более 612 попыток и не более 2% повторов**.

Меньшая доля тоже соответствует политике: это **верхняя граница**, а не цель израсходовать бюджет ровно до процента. Ошибка последней попытки списывает токен, но не запускает следующий retry; deadline также может остановить цепочку. По диагностике своего решения убедитесь, что повторы ограничил именно **бюджет**, а не только deadline или лимит попыток.

Если получили 600 уже в первом прогоне, проверьте, что ретраи включены, запас был полным и времени хватало хотя бы на один повтор. Если превысили рассчитанную границу, проверьте общий счётчик, атомарность и момент списания токена.

Повторите нагрузку **без рестарта Gateway и без снятия сбоя**, предварительно начав сбор в новый файл:

```sh
./bin/scooterctl logs api-gateway --outgoing -f --tail 0 \
  | tee /tmp/scooter-empty-budget.log
```

После завершения нагрузки подождите две секунды, остановите просмотр логов и посчитайте:

```sh
grep -c '"method"' /tmp/scooter-empty-budget.log
```

Теперь ожидаем **600 попыток и 0 retry**: без успешных вызовов токены не появились.

Для точного подсчёта дождитесь всех 600 завершённых запросов, не отправляйте параллельно запросы из Swagger и сохраняйте отдельный файл на каждый прогон.
