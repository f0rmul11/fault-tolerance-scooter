# 🛴 Модуль 3. «Карточка иногда не открывается — давайте просто повторим»

## 🎭 Контекст истории

Компания **ScooterFlow** развивает сервис аренды самокатов. Пользователь находит самокат на карте, открывает его карточку и решает, начинать ли бронирование.

Карточку отдаёт API Gateway. Чтобы получить номер, марку, владельца и признак доступности для новых бронирований, он синхронно обращается к **`Scooter.GetScooter`** по gRPC:

```text
Пользователь → API Gateway → Scooter.GetScooter → PostgreSQL Scooter
```

На первый взгляд — самая обычная интеграция между сервисами. Чтение карточки ничего не бронирует и не изменяет данные. Занятость самоката проверяет Rental при создании брони.

Вы — разработчик команды. Нужно уменьшить влияние временных сбоев на пользователей и убедиться, что ваше исправление не создаёт паразитную нагрузку на Scooter.

Поднимите стенд по [основному README](../../README.md). Все команды ниже выполняются из корня репозитория.

## 🚨 Что заметили в проде

> 💬 **Поддержка:** «Пользователь нажимает на самокат — получает ошибку. Нажимает ещё раз — карточка открывается. Самокат на месте, данные не менялись. Почему нельзя было показать их с первого раза?»

Проблема возникает не постоянно. В логах API Gateway отдельные обращения к Scooter заканчиваются `Unavailable`. Через десятки миллисекунд такой же запрос снова проходит.

Так могут выглядеть кратковременные сетевые сбои и перегрузки зависимости. Пока это гипотезы: один код ошибки не доказывает конкретную причину.

> 💬 **Коллега:** «Это же временная ошибка. Надо просто сделать retry».

И это звучит логично. Повторная попытка действительно может скрыть временный сбой от пользователя.

Но если ошибка перестанет быть редкой, каждый пользовательский запрос начнёт порождать несколько обращений в уже проблемный сервис.

## ⚠️ Бизнес-аксиома

> **Временный сбой по возможности не должен становиться ошибкой для пользователя.**
>
> **Попытки исправить этот сбой не должны сами становиться причиной деградации зависимости.**

У retry две цены: время пользователя и дополнительная работа системы. В этой домашней работе нужно учитывать обе.

## 🎯 SLO карточки самоката

Для корректных запросов существующего самоката договоримся о следующих целях:

| Условие | Что хотим получить |
| --- | --- |
| Время ответа | **p99 ≤ 300 мс** на входе API Gateway, с учётом всех попыток и пауз |
| `ok` и редкие временные ошибки (`rare_error`) | Стремимся к **99,9% успешных ответов** с правильной карточкой |
| Сильная деградация (`flaky`, `error`, длительный `slow`) | Ограниченное ожидание, понятная ошибка, контролируемая дополнительная нагрузка |
| Восстановление зависимости | Нормальные ответы возвращаются автоматически |

Проверяйте цель на одинаковой нагрузке: **20 пользовательских запросов в секунду, 10 минут**. Если ваш компьютер не выдерживает её даже в `ok`, сначала зафиксируйте устойчивую базовую нагрузку и используйте её во всех сравнениях.

99,9% — цель измерения, а не гарантия для каждой случайной выборки. Укажите число запросов и ошибок. Нельзя обещать такую доступность при 40% или 100% отказов только за счёт ограниченных retry.

В этом сценарии нет согласованного fallback: неизвестную карточку нельзя заменить выдуманным самокатом или успешным пустым ответом. Fallback и обычный circuit breaker разбираются в [модуле 4](../module-4/README.md).

## 🧰 Подготовка стенда

```sh
make cli
./bin/scooterctl doctor
./bin/scooterctl up --timeout 15m
./bin/scooterctl homework module-3 prepare
./bin/scooterctl homework module-3 status
```

`prepare` подготавливает эксперимент, выбирает существующий самокат из seed, готовит запросы для нагрузки и включает режим `ok`. Самокат доступен в командах под именем `available`: утилита сама подставляет его UUID.

`status` показывает выбранный самокат, активный режим, параметры сбоя, срок его действия и число реплик. Основные эксперименты проводим с **одной репликой API Gateway**, чтобы сопоставить поток запросов с её retry budget.

## 🎭 Режимы деградации Scooter

Для исследования доступны пять состояний зависимости:

| Режим | Что видит клиент API Gateway при вызове `Scooter.GetScooter` |
| --- | --- |
| `ok` | Запрос выполняется без искусственных ошибок и задержек |
| `error` | Каждая попытка получает gRPC `Unavailable` |
| `rare_error` | Каждая попытка с вероятностью **5%** получает `Unavailable` |
| `slow` | Вызов выполняется с растущей задержкой |
| `flaky` | Каждая попытка с вероятностью **40%** получает `Unavailable` |

В `slow` задержка начинается с **200 мс**, увеличивается на **100 мс каждые 500 мс** и достигает предела **5 секунд**. Рост зависит от времени после включения режима. Повторное включение `slow` начинает отсчёт заново.

Вероятность ошибки относится к **каждой RPC-попытке**, включая retry. В коротком прогоне доля ошибок может отличаться от 5% или 40%. `flaky` не означает строгое чередование успеха и ошибки.

### Переключение режимов

Выполняйте команды по одной, когда хотите изменить поведение зависимости:

```sh
./bin/scooterctl homework module-3 mode ok
./bin/scooterctl homework module-3 mode error --ttl 15m
./bin/scooterctl homework module-3 mode rare_error --ttl 15m
./bin/scooterctl homework module-3 mode slow --ttl 15m
./bin/scooterctl homework module-3 mode flaky --ttl 15m
```

Каждая команда заменяет предыдущий режим. `--ttl 15m` ограничивает длительность сбоя: через 15 минут обычное поведение восстанавливается автоматически. Переключение на `ok` прекращает искусственные ошибки и задержки для новых попыток сразу. Уже начавшиеся запросы могут завершиться позже или по своему deadline.

### На что влияет режим

Режим действует на вызовы **`API Gateway → Scooter.GetScooter`**. `error`, `rare_error` и `flaky` добавляют ошибки на этой связи, а `slow` — задержку. Проверяйте поведение через API Gateway: прямое обращение к Scooter в эксперимент не входит.

Остальные методы, БД, probes и вызовы `Rental → Scooter` продолжают работать как обычно. Pod могут оставаться `Ready`, даже когда выбранный вызов завершается ошибкой.

Переключение режима не требует изменения кода или перезапуска сервисов. Накопленный retry budget сохраняется — это позволяет проверить аварию и восстановление в одном прогоне.

## 🔁 Генератор нагрузки

Используем тот же [gRPC Framer](https://github.com/ozontech/framer), но подготовкой патронов, конвертацией, запуском и отчётами управляет `scooterctl`:

```sh
./bin/scooterctl homework module-3 mode ok
./bin/scooterctl homework module-3 load --rps 20 --duration 10m --timeout 3s
```

Запросы идут через API Gateway в `Scooter.GetScooter`. Следующая отправка не ждёт завершения предыдущего запроса.

Устанавливать Framer, искать порты и вручную конвертировать JSON не нужно. Подготовленные патроны повторяют чтение существующей карточки. Сам генератор не повторяет неуспешные запросы.

**`--rps 20` — пользовательские запросы в секунду.** Дополнительные обращения из вашего retry не входят в эти 20 RPS.

**`--timeout 3s` — внешний deadline запроса.** Он намеренно больше SLO: ответ за 2 секунды считается нарушением цели 300 мс, даже если генератор дождался успеха. Внутри приложения нужно выбрать собственный общий бюджет времени на все попытки.

### Что будет по итогам стрельбы

Утилита показывает и сохраняет:

- число отправленных запросов, успехи `ok` и ошибки `nook` с разбивкой по gRPC-кодам;
- заданный и фактический RPS, p95/p99 и долю ответов дольше 300 мс;
- детальный `report.phout` и читаемый отчёт: номер, время начала, тег, длительность, размер запроса, код результата;
- режим и параметры сбоя, время их изменения, параметры прогона и путь к результатам.

Статистика генератора описывает **результат для пользователя**. Сколько попыток API Gateway сделал в Scooter, выясняйте по диагностике исходящего клиента. После добавления retry эти числа могут существенно отличаться.

Для просмотра отдельного ответа используйте контрольный запрос:

```sh
./bin/scooterctl homework module-3 request --scooter available --timeout 3s
```

Проверьте карточку, код результата и длительность. Контрольные запросы — дополнительный трафик: выполняйте их отдельно от итогового прогона либо учитывайте в подсчётах.

## 🔹 Задание 1 — Устранение влияния временных сбоев

> 💬 **Поддержка:** «Карточка работает, если нажать второй раз. Сделайте так, чтобы пользователю не приходилось самому повторять запрос».

Вам предстоит **проанализировать и уменьшить влияние временных ошибок**, сохранив приемлемое время ответа.

### Ваша задача

- `max_attempts` задаёт **число всех попыток**, включая первоначальную. Значение `3` означает максимум два повтора.
- Для обязательного сценария повторяется только `Unavailable`. Бизнес-ошибки, `InvalidArgument`, `NotFound`, отмена исходного запроса и исчерпание общего deadline не повторяются.
- Между попытками действует **exponential backoff с jitter**. Выберите `initial_backoff`, `max_backoff`, `backoff_multiplier` и объясните выбранный вариант jitter.
- Все попытки и ожидания используют **один общий бюджет времени**, ограниченный также входящим deadline. Отмена контекста прерывает backoff и запрещает новую попытку.
- Retry находится в исходящем клиенте и включён только для выбранного метода. Обработчик gateway остаётся тонким; бизнес-логика Scooter не меняется.
- За повторы отвечает одна политика исходящего клиента. Не накладывайте свой цикл на включённую retry-политику gRPC: один отказ не должен порождать несколько независимых циклов повторения.

У gRPC также бывают прозрачные транспортные повторы без прикладной retry-политики. Учитывайте их при объяснении расхождения клиентских и сетевых счётчиков; не считайте отсутствие `retryPolicy` доказательством отсутствия любых повторов.

Начать разбор кода можно с [обработчика GetScooter](../../services/api-gateway/internal/app/scooter/v1/get_scooter.go), [инициализации gRPC-соединений](../../services/api-gateway/internal/init.go) и [ProxyMetadata](../../services/api-gateway/internal/pkg/grpc/intercept/client.go).

Продумайте порядок клиентских interceptor: наружу должен попадать результат итоговой попытки, с правильными metadata и кодом, а не накопленные ошибки промежуточных попыток. Generated-файлы не редактируйте.

После изменения сервиса пересоберите и разверните его штатными командами:

```sh
./bin/scooterctl build api-gateway --timeout 10m
./bin/scooterctl deploy api-gateway --timeout 10m
./bin/scooterctl homework module-3 status
```

После развёртывания проверьте активный режим через `status`. Перезапуск создаёт новый локальный бюджет с начальным запасом токенов — отметьте эту границу в отчёте.

### Проверьте своё решение

1. Снимите базовые показатели в `ok` без retry.
2. Включите `rare_error`, запустите ту же нагрузку и сохраните результат до исправления.
3. Добавьте ограниченные повторы исходящего `Scooter.GetScooter` на стороне API Gateway.
4. Повторите прогон и сравните ошибки, p95/p99 и число обращений в зависимость.
5. Переключитесь в `flaky`. Проверьте, какой ценой удаётся уменьшать число пользовательских ошибок.
6. Включите `slow`. Убедитесь, что приложение не тратит на каждую попытку новый полный бюджет времени.

### Вопросы на засыпку

1. Что произойдёт, если сильно увеличить `max_attempts`? Почему меньшая доля ошибок ещё не доказывает улучшение?
2. Как `initial_backoff`, `max_backoff` и `backoff_multiplier` влияют на время ответа и частоту повторов?
3. Зачем нужен jitter, если exponential backoff уже есть? Какую синхронизацию он разрушает?
4. Почему backoff не гарантирует ограничение суммарного числа повторов от всего потока?
5. В каких случаях retry бесполезен или опасен? Почему `DeadlineExceeded` нельзя безусловно трактовать как приглашение повторить?
6. Если два слоя разрешают по три попытки, сколько вызовов может получить последняя зависимость от одного исходного запроса?

Подберите параметры экспериментально. В отчёте покажите не только удачную конфигурацию, но и один пример, где дополнительные retry ухудшили время ответа или увеличили нагрузку без заметной пользы.

## 🔹 Задание 2 — Спасение утопающего

> 💬 **Дежурный:** «Пользователей больше не стало, а во время аварии запросов к Scooter стало втрое больше. Мы добавили retry, чтобы пережить сбой, но теперь мешаем сервису восстановиться».

При полном отказе `max_attempts` ограничивает работу одного запроса. Но при 20 пользовательских RPS и трёх попытках поток в зависимость всё ещё может приблизиться к 60 RPS.

**Цель:** ограничить дополнительную нагрузку от всего потока с помощью **retry budget**.

### 📌 Что такое retry budget

Это общий запас разрешённых повторов для выбранной зависимости. Мы переходим от вопроса «сколько раз повторить каждый запрос?» к вопросу «сколько дополнительной работы мы вообще готовы создать?».

В этой работе используем бюджет, **который пополняется успешными вызовами**:

```yaml
throttle_max_tokens: 20
throttle_token_ratio: 0.1
```

Это имена учебных параметров; готового раздела с ними в текущей конфигурации сервиса нет. Добавьте их в своё решение. Для проверяемости договоримся о точной семантике:

| Правило | Поведение |
| --- | --- |
| Область бюджета | Один экземпляр API Gateway, исходящий `Scooter.GetScooter`; бюджет общий для всех запросов и горутин |
| Начальный запас | `throttle_max_tokens`, здесь 20 |
| Первоначальная попытка | Не расходует токены и не запрещается из-за пустого бюджета |
| Каждый реально начатый retry | Расходует 1 токен; при запасе меньше 1 повтор запрещён |
| Успешный вызов зависимости | Пополняет запас на `throttle_token_ratio`, здесь 0,1; успех после retry учитывается один раз, как и успех первой попытки |
| Ошибка | Не пополняет бюджет |
| Максимальный запас | Не выше `throttle_max_tokens`; дробная часть сохраняется |
| Пополнение по таймеру | Отсутствует: без успехов новых токенов нет |

Проверка и списание токена должны быть атомарными. Проверяйте бюджет перед отправкой retry после backoff; не держите блокировку во время ожидания или RPC. Если повтор запрещён, верните последний отказ зависимости, сохранив семантику отмены/deadline.

Создание нового бюджета на каждый запрос уничтожает ограничение. Переключение режима и начало новой стрельбы не должны наполнять его заново.

### Как читать эти параметры

Если зависимость возвращает **200 успешных ответов в секунду**, при ratio `0.1` появляется до **20 токенов в секунду**. На длинном интервале это поддерживает примерно до 20 дополнительных попыток в секунду, пока сохраняется такой поток успехов.

Но это **не жёсткий лимит 20 RPS в каждую секунду**: накопленный запас допускает кратковременный всплеск. При полном отказе пополнение прекращается.

Для любого интервала без перезапуска бюджета проверяйте:

```text
R ≤ B₀ + ratio × S
```

Здесь `R` — реально начатые повторные попытки, `S` — успешные вызовы зависимости, `B₀` — запас токенов в начале интервала. Верхняя граница ёмкости может только уменьшить доступное число повторов.

**`throttle_token_ratio`** выбирают по допустимой дополнительной нагрузке, а **`throttle_max_tokens`** — по допустимому размеру всплеска. Увеличение ёмкости не увеличивает скорость пополнения. Значение 10% — условие эксперимента, а не универсально безопасная настройка для любой системы.

> 🔎 Не путайте эту модель со встроенным gRPC `retryThrottling`: там используются списание за определённые неудачные вызовы и порог половины `maxTokens`. Одинаково названные параметры не делают алгоритмы одинаковыми. Если берёте библиотеку, проверьте её семантику; для этого ДЗ требуется описанное выше списание за retry. [Документация gRPC](https://grpc.io/docs/guides/retry/).

### Проверьте своё решение

1. До включения бюджета снимите короткий прогон `error` с ограниченным retry из задания 1. Сравните пользовательские RPS и число попыток в зависимости.
2. Добавьте общий бюджет и повторите `error`. Покажите начальный всплеск, расход токенов и момент, после которого новые повторы запрещены.
3. Продолжайте подавать новые пользовательские запросы. Проверьте: первоначальные попытки идут, но без успехов бюджет не пополняется.
4. Во время той же стрельбы верните `ok`. Покажите восстановление успешных ответов и пополнение бюджета **без перезапуска gateway**.
5. Повторите `rare_error` и `flaky` с бюджетом. Сопоставьте выигрыш в доступности и разрешённую дополнительную нагрузку.

Для аварии и восстановления удобно использовать два терминала. В первом:

```sh
./bin/scooterctl homework module-3 mode error --ttl 15m
./bin/scooterctl homework module-3 load --rps 20 --duration 2m --timeout 3s
```

Во втором, после того как увидели исчерпание бюджета:

```sh
./bin/scooterctl homework module-3 mode ok
```

При `error`, отсутствии успехов и начальном запасе 20 разрешено **не более 20 retry суммарно на экземпляр**, а не 20 на каждый запрос и не 20 в секунду. Если к началу аварии запас меньше, повторов будет меньше. Учитывайте попытки, уже находившиеся в работе на границе смены режима.

### 🔍 Как убедиться, что всё работает

Сопоставьте отчёт генератора с диагностикой вашего клиента:

| Наблюдение | Что оно доказывает |
| --- | --- |
| Отчёт Framer | Сколько пользовательских запросов завершилось успехом/ошибкой и за какое время |
| Диагностика retry в API Gateway | Первые попытки, повторы, запреты по бюджету, успехи, текущий запас и причины остановки |

Для законченного набора вызовов число исходящих попыток должно складываться из первоначальных и повторных. На коротком временном срезе учитывайте незавершённые запросы и время записи логов.

В базовом стенде нет готового `/metrics` с retry-счётчиками. Для обязательной части достаточно структурированных логов и отчётов. Добавьте диагностику в выбранную реализацию защиты; не рассчитывайте восстановить внутренние retry только по пользовательским ошибкам.

Если хотите добавить метрики, полезны `grpc_client_retries_total`, `grpc_client_throttled_total` и `grpc_client_success_total`. Явно определите, что увеличивает каждый счётчик: запрещённый повтор не должен считаться отправленным RPC. `request_id` пригоден для логов, но не для лейблов временных рядов.

## ✅ Критерии успеха и сдача

| Проверка | Ожидаемый результат |
| --- | --- |
| `ok` | Правильная карточка, нет ненужных retry, базовое время ответа не испорчено |
| `rare_error` | Retry заметно уменьшают пользовательские ошибки; показано выполнение или объяснено отклонение от целей 99,9% / p99 ≤ 300 мс |
| `flaky` | Дополнительная нагрузка ограничена общим бюджетом; компромисс между ошибками и повторами объяснён |
| `error` | После расходования запаса retry прекращаются; новые первоначальные обращения продолжаются |
| `slow` и отмена | Общий deadline не обновляется на каждой попытке; ожидание backoff прерывается; после отмены нет новых попыток |
| Возврат в `ok` | Нормальные ответы и пополнение бюджета восстанавливаются без рестарта |
| Некорректный UUID / неизвестный самокат | В режиме `ok` сохраняются `InvalidArgument` / `NotFound`, повторов нет |

📦 Приложите:

1. Изменения кода и конфигурации API Gateway, реализующие выбранную retry-политику и бюджет.
2. Ответы на вопросы с привязкой к своему коду и используемой библиотеке.
3. Таблицу **режим → настройки → запросы → ошибки → p95/p99 → первые попытки → retry → запреты по бюджету**. Сравните исходный вариант, retry без бюджета и итоговое решение.
4. Хронологию `error → исчерпание бюджета → ok → восстановление`, с начальным запасом и проверкой ограничения `R ≤ B₀ + ratio × S`.
5. Проверки границ `max_attempts`, отмены во время backoff, конкурентного расходования бюджета и ошибок, которые нельзя повторять. Для изменённого Go-модуля запустите `go vet ./...` и `go test -race ./...`.

Формат короткого разбора: **симптом → причина → исправление → проверка → результат**.

После экспериментов верните обычный режим работы и завершите сценарий:

```sh
./bin/scooterctl homework module-3 mode ok
./bin/scooterctl homework module-3 cleanup
```

`cleanup` завершает эксперимент и возвращает стенд в обычный режим работы. Бизнес-данные, код решения и сохранённые отчёты остаются.

**Результат работы:** вы умеете уменьшать влияние временных сбоев, ограничивать цену повторов и подтверждать это измерениями.
