# 🛴 Модуль 3. «Карточка иногда не открывается — давайте просто повторим»

## 🎭 Контекст истории

Компания **ScooterFlow** развивает сервис аренды самокатов. Пользователь находит самокат на карте, открывает его карточку и решает, начинать ли бронирование.

Карточку отдаёт API Gateway. Чтобы получить номер, марку, владельца и признак доступности для новых бронирований, он синхронно обращается к **`Scooter.GetScooter`** по gRPC:

```text
Пользователь → API Gateway → Scooter.GetScooter → PostgreSQL Scooter
```

На первый взгляд — самая обычная интеграция между сервисами. Чтение карточки ничего не бронирует и не изменяет данные. Занятость самоката проверяет Rental при создании брони.

Вы — разработчик команды. Нужно уменьшить влияние временных сбоев на пользователей и убедиться, что ваше исправление не создаёт паразитную нагрузку на Scooter.

Поднимите стенд по [основному README](../../README.md). Все команды ниже выполняются из корня репозитория.

---

## 🚨 Что заметили в проде

> 💬 **Поддержка:** «Пользователь нажимает на самокат — получает ошибку. Нажимает ещё раз — карточка открывается. Самокат на месте, данные не менялись. Почему нельзя было показать их с первого раза?»

Проблема возникает не постоянно. В логах API Gateway отдельные обращения к Scooter заканчиваются `Unavailable`. Через десятки миллисекунд такой же запрос снова проходит.

Так могут выглядеть кратковременные сетевые сбои и перегрузки зависимости. Пока это гипотезы: один код ошибки не доказывает конкретную причину.

> 💬 **Коллега:** «Это же временная ошибка. Надо просто сделать retry».

И это звучит логично. Повторная попытка действительно может скрыть временный сбой от пользователя.

Но если ошибка перестанет быть редкой, каждый пользовательский запрос начнёт порождать несколько обращений в уже проблемный сервис.

## ⚠️ Бизнес-аксиома

> **Временный сбой по возможности не должен становиться ошибкой для пользователя.**
>
> **Попытки исправить этот сбой не должны сами становиться причиной деградации зависимости.**

У retry две цены: время пользователя и дополнительная работа системы. В этой домашней работе нужно учитывать обе.

## 🎯 SLO карточки самоката

Для корректных запросов существующего самоката договоримся о следующих целях:

| Условие | Что хотим получить |
| --- | --- |
| Время ответа | **p99 ≤ 300 мс** на входе API Gateway, с учётом всех попыток и пауз |
| Без сбоев и при 5% `Unavailable` | Стремимся к **99,9% успешных ответов** с правильной карточкой |
| 40–100% `Unavailable` или большая задержка | Ограниченное ожидание, понятная ошибка, контролируемая дополнительная нагрузка |
| Восстановление зависимости | Нормальные ответы возвращаются автоматически |

Проверяйте цель на одинаковой нагрузке: **20 пользовательских запросов в секунду, 10 минут**. Если ваш компьютер не выдерживает её даже без искусственных сбоев, сначала зафиксируйте устойчивую базовую нагрузку и используйте её во всех сравнениях.

99,9% — цель измерения, а не гарантия для каждой случайной выборки. Укажите число запросов и ошибок. Нельзя обещать такую доступность при 40% или 100% отказов только за счёт ограниченных retry.

В этом сценарии нет согласованного fallback: неизвестную карточку нельзя заменить выдуманным самокатом или успешным пустым ответом. Fallback и обычный circuit breaker разбираются в [модуле 4](../module-4/README.md).

## 🧰 Подготовка стенда

```sh
make cli
./bin/scooterctl doctor
./bin/scooterctl up --timeout 15m
./bin/scooterctl status api-gateway
./bin/scooterctl access
```

Основные эксперименты проводим с **одной репликой API Gateway**, чтобы сопоставить поток запросов с её retry budget. Проверьте число реплик через `status`.

Откройте Swagger по адресу из `access`. Выполните `GET /v1/scooters`, выберите существующую карточку и проверьте `GET /v1/scooters/{scooter_id}`. В [get-scooter.json](get-scooter.json) уже указан UUID самоката из стартовых данных; если данные изменены, замените его на выбранный UUID. Чтение карточки не требует свободного для аренды самоката.

Все дальнейшие запросы идут через API Gateway. Бизнес-данные во время подготовки не сбрасываются.

## 🎭 Создаём сбой на связи между сервисами

Мы явно задаём, **где и что сломать**. В первом терминале включите редкие ошибки:

```sh
./bin/scooterctl fault api-gateway scooter \
  --method GetScooter \
  --unavailable --percent 5 --duration 15m
```

Дождитесь `ACTIVE`. Теперь случайные **5% попыток** `API Gateway → Scooter.GetScooter` получают gRPC `Unavailable` **до обработки запроса сервисом Scooter**. Процент относится к каждой попытке, включая retry. В коротком прогоне доля ошибок может отличаться от заданной.

Команда остаётся работать в первом терминале. Во втором отправляйте запросы или запускайте нагрузку. **Ctrl+C в первом терминале снимает сбой**; через 15 минут команда также снимет его сама. Дождитесь сообщения «Правило снято» перед следующим экспериментом.

Для более частых ошибок остановите предыдущую команду и запустите:

```sh
./bin/scooterctl fault api-gateway scooter \
  --method GetScooter \
  --unavailable --percent 40 --duration 15m
```

Для полной недоступности выбранного вызова:

```sh
./bin/scooterctl fault api-gateway scooter \
  --method GetScooter \
  --unavailable --percent 100 --duration 15m
```

Для медленной зависимости:

```sh
./bin/scooterctl fault api-gateway scooter \
  --method GetScooter \
  --slowdown 500ms --duration 15m
```

Последняя команда добавляет **500 мс к каждой попытке перед обработкой в Scooter**. По отдельности повторите эксперимент с `--slowdown 200ms` и `--slowdown 2s`. Задержка постоянна: её значение не меняется само по себе.

### На что влияет команда

Только на выбранную связь и метод. Остальные методы, БД, probes и вызовы `Rental → Scooter` работают как обычно. Pod могут оставаться `Ready`, даже когда выбранный вызов завершается ошибкой. Прямой запрос в Scooter не проверяет этот сбой.

Сервисы не перезапускаются: накопленный retry budget сохраняется. Уже задержанные запросы после снятия сбоя могут завершиться позже или по deadline.

Если терминал аварийно закрылся, процесс был убит или снятие сбоя завершилось ошибкой, выполните:

```sh
./bin/scooterctl fault api-gateway scooter --clear
```

Это снимает искусственные ошибки и задержки. Пока команда `fault` работает, останавливайте её через Ctrl+C. Во время измерения не выполняйте `up`, `deploy`, `restart` или `reset`: они меняют условия эксперимента.

## 🔁 Генератор нагрузки

Используем [gRPC Framer](https://github.com/ozontech/framer), встроенный в `scooterctl`. Утилита сама устанавливает закреплённую версию при первом запуске и преобразует JSON в запрос генератора. Для первой установки нужны Go, Git и доступ к сети.

Во втором терминале:

```sh
./bin/scooterctl load \
  --addr 127.0.0.1:19090 \
  --method api_gateway.scooter.v1.ScooterService/GetScooter \
  --data-file homeworks/module-3/get-scooter.json \
  --rps 20 --duration 10m --request-timeout 3s
```

Что делает команда:

- `--addr` — gRPC-вход API Gateway из `scooterctl access`; если меняли порты, подставьте свой;
- `--method` — публичный RPC получения карточки;
- `--data-file` — JSON-тело каждого запроса: откройте файл и проверьте UUID;
- `--rps 20` — 20 **пользовательских запросов в секунду**; retry приложения не входят в эти 20 RPS;
- `--duration 10m` — время подачи нагрузки;
- `--request-timeout 3s` — внешний deadline **одного запроса**, а не всей команды.

Следующая отправка планируется независимо от завершения предыдущего запроса. Сам генератор не повторяет неуспешные запросы. Сравнивайте фактический RPS с заданным: компьютер тоже может стать ограничением эксперимента.

Внешний deadline намеренно больше SLO: ответ за 2 секунды нарушает цель 300 мс, даже если генератор дождался успеха. В приложении нужно выбрать собственный общий бюджет времени на все попытки.

### Что будет по итогам стрельбы

В конце команда выводит результат и путь к каталогу `.local/scooterctl/load/...`:

- `summary.txt` и `summary.json`: отправленные и завершённые запросы, успехи и ошибки, коды результата, заданный RPS и число завершений на секунду подачи нагрузки, p95/p99, доля ответов дольше 300 мс;
- `report.phout`: исходный отчёт Framer;
- `requests.tsv`: читаемая таблица с номером, временем начала, тегом, длительностью, размером запроса и кодом результата.

Процентили включают **и успехи, и ошибки**, с округлением вверх до миллисекунды. Быстрые ошибки не означают выполнение цели доступности. При Ctrl+C сохраняются завершённые запросы, а отчёт помечается как неполный; итоговые сравнения проводите на полных прогонах.

В кодах отчёта `grpc_0` — успех, `grpc_14` — `Unavailable`, `grpc_4` — `DeadlineExceeded`. При истечении deadline также возможен `rst_8`: сервер завершил HTTP/2-поток через CANCEL. Это ошибка транспорта, а не успешный ответ.

Запишите рядом с результатами команду сбоя, время его включения/снятия и настройки своего решения. Утилита не знает внутренние параметры вашего retry budget.

Для проверки содержимого ответа используйте Swagger или обычный HTTP-запрос:

```sh
curl --max-time 3 -sS -w '\nHTTP %{http_code}, время %{time_total}s\n' \
  http://127.0.0.1:18080/v1/scooters/3499a1fb-030c-47a8-bcd2-0ce8304d6a22
```

Подставьте тот же UUID, что в JSON. Контрольные запросы — дополнительный трафик: выполняйте их отдельно от итогового прогона либо учитывайте в подсчётах.

### Сколько попыток действительно ушло в Scooter

В третьем терминале **до запуска нагрузки** откройте:

```sh
./bin/scooterctl logs api-gateway --outgoing -f --tail 0
```

Одна JSON-строка — одна завершившаяся попытка `Gateway → Scooter.GetScooter`, включая искусственно отклонённые. В ней есть `request_id`, метод, время начала, длительность, gRPC-статус и признаки сбоя. `FI` означает искусственный отказ, `DI` — искусственную задержку. Повторы одного пользовательского запроса имеют один `request_id`.

Для сохранения наблюдений:

```sh
./bin/scooterctl logs api-gateway --outgoing -f --tail 0 | tee /tmp/scooter-attempts.log
```

Дождитесь окончания нагрузки и завершения оставшихся запросов, подождите ещё две секунды для доставки логов, затем остановите просмотр. Не считайте служебную строку `Pod:` или строки без поля `method` попытками. Сохраняйте отдельный файл для каждого прогона.

Число завершённых исходящих попыток в сохранённом файле:

```sh
grep -c '"method"' /tmp/scooter-attempts.log
```

Для полного прогона корректных запросов без другого трафика сравните это число с `Отправлено` в отчёте генератора. Разница показывает дополнительные обращения; по `request_id` можно проверить отдельные повторы. При отмене и незавершённых запросах сначала разберите границы измерения.

Логи вашего retry и бюджета смотрите отдельно:

```sh
./bin/scooterctl logs api-gateway -f --tail 0
```

Отчёт Framer показывает **результат для пользователя**. Исходящие логи показывают **цену этого результата в RPC-попытках**. Диагностика вашего решения объясняет, почему повтор был разрешён или запрещён.

## 🔹 Задание 1 — Устранение влияния временных сбоев

> 💬 **Поддержка:** «Карточка работает, если нажать второй раз. Сделайте так, чтобы пользователю не приходилось самому повторять запрос».

Вам предстоит **проанализировать и уменьшить влияние временных ошибок**, сохранив приемлемое время ответа.

### Ваша задача

- `max_attempts` задаёт **число всех попыток**, включая первоначальную. Значение `3` означает максимум два повтора.
- Для обязательного сценария повторяется только `Unavailable`. Бизнес-ошибки, `InvalidArgument`, `NotFound`, отмена исходного запроса и исчерпание общего deadline не повторяются.
- Между попытками действует **exponential backoff с jitter**. Выберите `initial_backoff`, `max_backoff`, `backoff_multiplier` и объясните выбранный вариант jitter.
- Все попытки и ожидания используют **один общий бюджет времени**, ограниченный также входящим deadline. Отмена контекста прерывает backoff и запрещает новую попытку.
- Retry находится в исходящем клиенте и включён только для выбранного метода. Обработчик gateway остаётся тонким; бизнес-логика Scooter не меняется.
- За повторы отвечает одна политика исходящего клиента. Не накладывайте свой цикл на включённую retry-политику gRPC: один отказ не должен порождать несколько независимых циклов повторения.

У gRPC также бывают прозрачные транспортные повторы без прикладной retry-политики. Учитывайте их при объяснении расхождения клиентских и сетевых счётчиков; не считайте отсутствие `retryPolicy` доказательством отсутствия любых повторов.

Начать разбор кода можно с [обработчика GetScooter](../../services/api-gateway/internal/app/scooter/v1/get_scooter.go), [инициализации gRPC-соединений](../../services/api-gateway/internal/init.go) и [ProxyMetadata](../../services/api-gateway/internal/pkg/grpc/intercept/client.go).

Продумайте порядок клиентских interceptor: наружу должен попадать результат итоговой попытки, с правильными metadata и кодом, а не накопленные ошибки промежуточных попыток. Generated-файлы не редактируйте.

После изменения сервиса пересоберите и разверните его штатными командами:

```sh
./bin/scooterctl build api-gateway --timeout 10m
./bin/scooterctl deploy api-gateway --timeout 10m
./bin/scooterctl status api-gateway
```

Перед развёртыванием остановите нагрузку и снимите сбой. После развёртывания проверьте готовность через `status` и заново включите нужный сбой. Перезапуск создаёт новый локальный бюджет с начальным запасом токенов — отметьте эту границу в отчёте.

### Проверьте своё решение

1. Снимите базовые показатели без искусственных сбоев и без retry.
2. Включите `--unavailable --percent 5`, запустите ту же нагрузку и сохраните результат до исправления.
3. Добавьте ограниченные повторы исходящего `Scooter.GetScooter` на стороне API Gateway.
4. Повторите прогон и сравните ошибки, p95/p99 и число обращений в зависимость.
5. Снимите сбой и включите `--unavailable --percent 40`. Проверьте, какой ценой удаётся уменьшать число пользовательских ошибок.
6. Проверьте `--slowdown 200ms`, затем `500ms` и `2s` в отдельных прогонах. Убедитесь, что приложение не тратит на каждую попытку новый полный бюджет времени.

### Вопросы на засыпку

1. Что произойдёт, если сильно увеличить `max_attempts`? Почему меньшая доля ошибок ещё не доказывает улучшение?
2. Как `initial_backoff`, `max_backoff` и `backoff_multiplier` влияют на время ответа и частоту повторов?
3. Зачем нужен jitter, если exponential backoff уже есть? Какую синхронизацию он разрушает?
4. Почему backoff не гарантирует ограничение суммарного числа повторов от всего потока?
5. В каких случаях retry бесполезен или опасен? Почему `DeadlineExceeded` нельзя безусловно трактовать как приглашение повторить?
6. Если два слоя разрешают по три попытки, сколько вызовов может получить последняя зависимость от одного исходного запроса?

Подберите параметры экспериментально. В отчёте покажите не только удачную конфигурацию, но и один пример, где дополнительные retry ухудшили время ответа или увеличили нагрузку без заметной пользы.

## 🔹 Задание 2 — Спасение утопающего

> 💬 **Дежурный:** «Пользователей больше не стало, а во время аварии запросов к Scooter стало втрое больше. Мы добавили retry, чтобы пережить сбой, но теперь мешаем сервису восстановиться».

При полном отказе `max_attempts` ограничивает работу одного запроса. Но при 20 пользовательских RPS и трёх попытках поток в зависимость всё ещё может приблизиться к 60 RPS.

**Цель:** ограничить дополнительную нагрузку от всего потока с помощью **retry budget**.

### 📌 Что такое retry budget

Это общий запас разрешённых повторов для выбранной зависимости. Мы переходим от вопроса «сколько раз повторить каждый запрос?» к вопросу «сколько дополнительной работы мы вообще готовы создать?».

В этой работе используем бюджет, **который пополняется успешными вызовами**:

```yaml
throttle_max_tokens: 20
throttle_token_ratio: 0.1
```

Это имена учебных параметров; готового раздела с ними в текущей конфигурации сервиса нет. Добавьте их в своё решение. Для проверяемости договоримся о точной семантике:

| Правило | Поведение |
| --- | --- |
| Область бюджета | Один экземпляр API Gateway, исходящий `Scooter.GetScooter`; бюджет общий для всех запросов и горутин |
| Начальный запас | `throttle_max_tokens`, здесь 20 |
| Первоначальная попытка | Не расходует токены и не запрещается из-за пустого бюджета |
| Каждый реально начатый retry | Расходует 1 токен; при запасе меньше 1 повтор запрещён |
| Успешный вызов зависимости | Пополняет запас на `throttle_token_ratio`, здесь 0,1; успех после retry учитывается один раз, как и успех первой попытки |
| Ошибка | Не пополняет бюджет |
| Максимальный запас | Не выше `throttle_max_tokens`; дробная часть сохраняется |
| Пополнение по таймеру | Отсутствует: без успехов новых токенов нет |

Проверка и списание токена должны быть атомарными. Проверяйте бюджет перед отправкой retry после backoff; не держите блокировку во время ожидания или RPC. Если повтор запрещён, верните последний отказ зависимости, сохранив семантику отмены/deadline.

Создание нового бюджета на каждый запрос уничтожает ограничение. Включение/снятие сбоя и начало новой стрельбы не должны наполнять его заново.

### Как читать эти параметры

Если зависимость возвращает **200 успешных ответов в секунду**, при ratio `0.1` появляется до **20 токенов в секунду**. На длинном интервале это поддерживает примерно до 20 дополнительных попыток в секунду, пока сохраняется такой поток успехов.

Но это **не жёсткий лимит 20 RPS в каждую секунду**: накопленный запас допускает кратковременный всплеск. При полном отказе пополнение прекращается.

Для любого интервала без перезапуска бюджета проверяйте:

```text
R ≤ B₀ + ratio × S
```

Здесь `R` — реально начатые повторные попытки, `S` — успешные вызовы зависимости, `B₀` — запас токенов в начале интервала. Верхняя граница ёмкости может только уменьшить доступное число повторов.

**`throttle_token_ratio`** выбирают по допустимой дополнительной нагрузке, а **`throttle_max_tokens`** — по допустимому размеру всплеска. Увеличение ёмкости не увеличивает скорость пополнения. Значение 10% — условие эксперимента, а не универсально безопасная настройка для любой системы.

> 🔎 Не путайте эту модель со встроенным gRPC `retryThrottling`: там используются списание за определённые неудачные вызовы и порог половины `maxTokens`. Одинаково названные параметры не делают алгоритмы одинаковыми. Если берёте библиотеку, проверьте её семантику; для этого ДЗ требуется описанное выше списание за retry. [Документация gRPC](https://grpc.io/docs/guides/retry/).

### Проверьте своё решение

1. До включения бюджета снимите короткий прогон со 100% `Unavailable` с ограниченным retry из задания 1. Сравните пользовательские RPS и число попыток в зависимости.
2. Добавьте общий бюджет и повторите тот же сбой. Покажите начальный всплеск, расход токенов и момент, после которого новые повторы запрещены.
3. Продолжайте подавать новые пользовательские запросы. Проверьте: первоначальные попытки идут, но без успехов бюджет не пополняется.
4. Во время той же стрельбы снимите сбой через Ctrl+C в терминале `fault`. Покажите восстановление успешных ответов и пополнение бюджета **без перезапуска gateway**.
5. Повторите 5% и 40% `Unavailable` с бюджетом. Сопоставьте выигрыш в доступности и разрешённую дополнительную нагрузку.

### 🧪 Конкретный пример: 600 запросов → максимум 620 попыток

Проверьте бюджет двумя последовательными прогонами. Условия: **одна реплика Gateway**, `max_attempts: 3`, начальный запас **20**, пополнение **0.1 за успех**, без постороннего трафика. Backoff и общий deadline должны позволять выполнить повторы при быстром `Unavailable`.

**1. Начните с полного бюджета.** Остановите предыдущую нагрузку и сбои. После развёртывания своего решения перезапустите Gateway и дождитесь готовности:

```sh
./bin/scooterctl restart api-gateway --timeout 2m
```

Это единственный перезапуск в данном эксперименте. Начальный запас нового процесса — 20 токенов.

**2. В терминале 1 включите полный отказ и дождитесь `ACTIVE`:**

```sh
./bin/scooterctl fault api-gateway scooter \
  --method GetScooter \
  --unavailable --percent 100 --duration 15m
```

Не снимайте сбой между прогонами: без успешных вызовов бюджет не должен пополняться.

**3. В терминале 2 начните сохранять попытки до запуска нагрузки:**

```sh
./bin/scooterctl logs api-gateway --outgoing -f --tail 0 \
  | tee /tmp/scooter-budget-first.log
```

**4. В терминале 3 отправьте 600 запросов — 20 RPS в течение 30 секунд:**

```sh
./bin/scooterctl load \
  --addr 127.0.0.1:19090 \
  --method api_gateway.scooter.v1.ScooterService/GetScooter \
  --data-file homeworks/module-3/get-scooter.json \
  --rps 20 --duration 30s --request-timeout 3s
```

Проверьте в отчёте: отправлено и завершено **600** запросов. После окончания нагрузки подождите ещё две секунды, остановите **только просмотр логов в терминале 2** через Ctrl+C и посчитайте попытки:

```sh
grep -c '"method"' /tmp/scooter-budget-first.log
```

Ожидаем **600 первоначальных + 20 повторных = 620 попыток**. Это верхняя граница: успешных вызовов нет, поэтому новые токены не появляются. По диагностике своего решения убедитесь, что все 20 токенов потрачены и запас стал нулевым. Если попыток меньше 620, проверьте настройки retry, deadline и полноту логов: само по себе небольшое число попыток ещё не доказывает работу бюджета.

**5. Повторите ту же нагрузку без рестарта Gateway и без снятия сбоя.** Сначала в терминале 2 откройте новый файл:

```sh
./bin/scooterctl logs api-gateway --outgoing -f --tail 0 \
  | tee /tmp/scooter-budget-second.log
```

В терминале 3 повторите команду `load` из шага 4. После завершения снова подождите две секунды, остановите просмотр логов и посчитайте:

```sh
grep -c '"method"' /tmp/scooter-budget-second.log
```

| Прогон | Пользовательские запросы | Запас в начале | Retry | Всего попыток |
| --- | ---: | ---: | ---: | ---: |
| Первый | 600 | 20 | Не более 20 | Не более **620** |
| Второй, после исчерпания запаса | 600 | 0 | **0** | **600** |

В обоих прогонах все пользовательские запросы завершатся ошибкой — зависимость полностью недоступна. Разница видна в дополнительной нагрузке. Первоначальные обращения продолжаются даже при пустом бюджете. Если второй прогон снова расходует 20 токенов, хотя успехов и рестарта не было, ищите ошибочное пересоздание бюджета или пополнение по таймеру.

Оставьте сбой включённым и перейдите к проверке восстановления ниже. Если завершаете эксперимент здесь, снимите сбой через Ctrl+C в терминале 1 и дождитесь сообщения «Правило снято».

### Восстановление без рестарта

Для аварии и восстановления используйте отдельные терминалы. Если продолжаете предыдущий эксперимент, оставьте уже работающую команду `fault` в терминале 1; повторно запускать её и перезапускать Gateway не нужно.

**Терминал 1 — если сбой ещё не включён, включить его и дождаться `ACTIVE`:**

```sh
./bin/scooterctl fault api-gateway scooter \
  --method GetScooter \
  --unavailable --percent 100 --duration 15m
```

**Терминал 2 — подать нагрузку:**

```sh
./bin/scooterctl load \
  --addr 127.0.0.1:19090 \
  --method api_gateway.scooter.v1.ScooterService/GetScooter \
  --data-file homeworks/module-3/get-scooter.json \
  --rps 20 --duration 2m --request-timeout 3s
```

Когда по логам увидели исчерпание бюджета, нажмите **Ctrl+C в терминале 1**. Нагрузку в терминале 2 оставьте работать. Покажите восстановление без рестарта Gateway.

При 100% `Unavailable`, отсутствии успехов и начальном запасе 20 разрешено **не более 20 retry суммарно на экземпляр**, а не 20 на каждый запрос и не 20 в секунду. Если к началу аварии запас меньше, повторов будет меньше. Учитывайте попытки, уже находившиеся в работе на границе снятия сбоя.

### 🔍 Как убедиться, что всё работает

Сопоставьте отчёт генератора с диагностикой вашего клиента:

| Наблюдение | Что оно доказывает |
| --- | --- |
| Отчёт Framer | Сколько пользовательских запросов завершилось успехом/ошибкой и за какое время |
| `logs api-gateway --outgoing` | Все завершённые попытки GetScooter на выбранной связи, включая искусственные отказы |
| Диагностика retry в API Gateway | Первые попытки, повторы, запреты по бюджету, успехи, текущий запас и причины остановки |

Для законченного набора вызовов число исходящих попыток должно складываться из первоначальных и повторных. На коротком временном срезе учитывайте незавершённые запросы и время записи логов.

В базовом стенде нет готового `/metrics` с retry-счётчиками. Для обязательной части достаточно структурированных логов и отчётов. Добавьте диагностику в выбранную реализацию защиты; не рассчитывайте восстановить внутренние retry только по пользовательским ошибкам.

Если хотите добавить метрики, полезны `grpc_client_retries_total`, `grpc_client_throttled_total` и `grpc_client_success_total`. Явно определите, что увеличивает каждый счётчик: запрещённый повтор не должен считаться отправленным RPC. `request_id` пригоден для логов, но не для лейблов временных рядов.

## ✅ Критерии успеха и сдача

| Проверка | Ожидаемый результат |
| --- | --- |
| Без искусственных сбоев | Правильная карточка, нет ненужных retry, базовое время ответа не испорчено |
| 5% `Unavailable` | Retry заметно уменьшают пользовательские ошибки; показано выполнение или объяснено отклонение от целей 99,9% / p99 ≤ 300 мс |
| 40% `Unavailable` | Дополнительная нагрузка ограничена общим бюджетом; компромисс между ошибками и повторами объяснён |
| 100% `Unavailable` | После расходования запаса retry прекращаются; новые первоначальные обращения продолжаются |
| Задержка и отмена | Общий deadline не обновляется на каждой попытке; ожидание backoff прерывается; после отмены нет новых попыток |
| Снятие сбоя | Нормальные ответы и пополнение бюджета восстанавливаются без рестарта |
| Некорректный UUID / неизвестный самокат | Без искусственных сбоев сохраняются `InvalidArgument` / `NotFound`, повторов нет |

📦 Приложите:

1. Изменения кода и конфигурации API Gateway, реализующие выбранную retry-политику и бюджет.
2. Ответы на вопросы с привязкой к своему коду и используемой библиотеке.
3. Таблицу **сбой → настройки → запросы → ошибки → p95/p99 → первые попытки → retry → запреты по бюджету**. Сравните исходный вариант, retry без бюджета и итоговое решение.
4. Хронологию `100% Unavailable → исчерпание бюджета → снятие сбоя → восстановление`, с начальным запасом и проверкой ограничения `R ≤ B₀ + ratio × S`.
5. Проверки границ `max_attempts`, отмены во время backoff, конкурентного расходования бюджета и ошибок, которые нельзя повторять. Для изменённого Go-модуля запустите `go vet ./...` и `go test -race ./...`.

Формат короткого разбора: **симптом → причина → исправление → проверка → результат**.

После экспериментов остановите `fault` через **Ctrl+C** и дождитесь снятия правила. Если команда завершилась аварийно:

```sh
./bin/scooterctl fault api-gateway scooter --clear
```

Бизнес-данные, код решения и сохранённые отчёты остаются на месте.

**Результат работы:** вы умеете уменьшать влияние временных сбоев, ограничивать цену повторов и подтверждать это измерениями.
