# 🛴 Модуль 4. «Скидка, которая зависела от истории поездок»

## 🎭 Контекст истории

Компания **ScooterFlow** развивает сервис аренды самокатов. Постоянным пользователям положена персональная скидка: чем больше завершённых поездок, тем она выше.

| Завершённые поездки | Скидка |
| --- | --- |
| От 0 до 9 включительно | **0%** |
| От 10 до 49 включительно | **10%** |
| От 50 и больше | **20%** |

Пользователь открывает личный кабинет и видит свою скидку. За этот сценарий отвечает ручка **`Profile.GetDiscount`**.

Profile проверяет пользователя в своей БД, затем синхронно обращается к **`Pricing.GetCompletedTripsCount`** по gRPC. Pricing возвращает количество завершённых расчётов поездок, а Profile выбирает скидку по таблице выше.

```text
Пользователь → API Gateway → Profile.GetDiscount
                                 │
                                 └── gRPC → Pricing.GetCompletedTripsCount
                                                │
                                                └── PostgreSQL Pricing
```

Pricing считает только поездки в состоянии `COMPLETED`. Брони, активные и отменённые поездки в программу лояльности не входят. Данные приходят в Pricing через Kafka, поэтому только что завершённая поездка может появиться в счётчике с небольшой задержкой. Для личного кабинета это допустимо.

`GetCompletedTripsCount` читает собственную БД Pricing. Он не вызывает Profile. Существующий вызов `Pricing → Profile.GetProfile`, который нужен при обработке события бронирования, — другой сценарий. `GetProfile` по-прежнему читает локальные данные.

Именно синхронная зависимость **`Profile → Pricing`** и становится источником наших проблем.

## 🚨 Что случилось в проде

> 💬 **Поддержка:** «Пользователи жалуются: раздел со скидкой то открывается, то возвращает ошибку. Иногда приходится ждать несколько секунд. При этом имя, почта и подписка загружаются нормально».

В определённый момент Pricing начал вести себя нестабильно:

- периодически отвечать ошибками;
- иногда резко тормозить;
- «флапать» — то работать, то нет;
- отвечать всё медленнее в течение инцидента.

Это сказалось на сервисе профиля. Пользователи начали получать ошибки, долгие ответы и таймауты при запросе скидки.

Хотя **сам Profile и его база полностью работоспособны**. Он просто зависит от нестабильного downstream-сервиса.

---

## ⚠️ Бизнес-аксиома

> **Проблема с расчётом скидки не должна ломать личный кабинет.**

Если историю поездок сейчас получить невозможно, допустимо вернуть **0% с явным признаком деградации**. Интерфейс покажет: «Персональная скидка временно недоступна». Пользователь сможет продолжить работу с приложением.

При этом есть важное различие:

| Ситуация | `discount_percent` | `degraded` | `source` |
| --- | --- | --- | --- |
| Pricing подтвердил 3 завершённые поездки | `0` | `false` | `pricing` |
| Pricing подтвердил 12 завершённых поездок | `10` | `false` | `pricing` |
| Pricing подтвердил 55 завершённых поездок | `20` | `false` | `pricing` |
| Историю получить не удалось, сработал fallback | `0` | `true` | `fallback` |

В fallback количество поездок **неизвестно**: нельзя подменять его нулём и утверждать, что пользователь ещё ни разу не ездил.

В этой работе `GetDiscount` обслуживает отображение скидки в личном кабинете. Его ответ не фиксирует цену, не меняет подписку и не переписывает сохранённую стоимость поездок. Решение о применении скидки при бронировании и списании требует отдельного бизнес-контракта.

Деградация разрешена при техническом сбое зависимости. Некорректный `user_id` или отсутствующий пользователь должны оставаться ошибками. Отказ собственной БД Profile также нельзя маскировать ответом «скидка 0%».

Система должна **деградировать**, сохраняя смысл ответа.

## 🧠 Что нужно понять инженеру

В этой истории есть четыре разные проблемы:

1. Profile напрямую зависит от доступности Pricing.
2. Profile продолжает нагружать Pricing, даже когда обращения к нему почти наверняка закончатся неудачей.
3. Когда Pricing тормозит, Profile слишком долго его ждёт и нарушает свой SLO.
4. Попытка «просто добавить ретраи» увеличивает число обращений к проблемной зависимости.

Вам предстоит решить все четыре и объяснить, как защитные механизмы работают вместе.

## 🎯 SLO получения скидки

Для корректных запросов существующих пользователей:

- **p99 времени ответа — не более 300 мс** на стороне клиента, включая прохождение через API Gateway.
- **Не менее 99,9% запросов — успешные**. Корректный degraded response считается успехом по доступности.
- В режиме `ok` возвращается рассчитанная скидка. Постоянно отдавать fallback, чтобы формально выполнить SLO, нельзя.
- Доля деградированных ответов учитывается отдельно: «API доступно» и «скидка рассчитана по истории» — разные показатели.

Для итоговой проверки используйте прогоны по **10 минут при 2 RPS** и указывайте число запросов. Коротких прогонов достаточно для исследования переходов CB, но недостаточно для уверенного вывода о редких ошибках. Результат учебного прогона не заменяет длительное измерение production SLO.

Клиентский deadline **3 секунды** нужен для экспериментов. Он не заменяет требование ответить за 300 мс.

## 🧰 Подготовка стенда

Все команды выполняются из корня репозитория ScooterFlow. Требования к окружению описаны в основном README.

```sh
make cli
./bin/scooterctl doctor
./bin/scooterctl up --timeout 15m
./bin/scooterctl homework module-4 prepare
./bin/scooterctl homework module-4 status
```

`prepare` подготавливает учебные данные, подключает прокси для экспериментов между Profile и Pricing и включает режим `ok`. В наборе есть три пользователя: `new` с 0 поездок, `regular` с 12 и `frequent` с 55. Утилита сама сопоставляет эти имена с UUID и использует их в запросах.

Начинайте эксперименты после завершения подготовки и обработки учебных событий. Количество поездок во время прогона должно оставаться неизменным.

`status` показывает активный режим, время его включения, параметры сбоя, срок его действия и число реплик. Основные эксперименты проводим с **одной репликой Profile**: так проще сопоставить входящий поток со статистикой конкретного circuit breaker.

## 🎭 Режимы деградации Pricing

Для исследования доступны те же пять состояний зависимости:

| Режим | Что видит клиент Profile |
| --- | --- |
| `ok` | Запрос проходит в Pricing без искусственных ошибок и задержек |
| `error` | Каждая попытка получает gRPC `Unavailable` |
| `rare_error` | Каждая попытка с вероятностью **5%** получает `Unavailable` |
| `slow` | Перед передачей запроса в Pricing добавляется растущая задержка |
| `flaky` | Каждая попытка с вероятностью **40%** получает `Unavailable` |

В `slow` задержка начинается с **200 мс**, увеличивается на **100 мс каждые 500 мс** и достигает предела **5 секунд**. Рост зависит от времени после включения режима, а не от количества запросов. Повторное включение `slow` начинает отсчёт заново.

Вероятность относится к **каждой RPC-попытке**, включая retry. В коротком прогоне доля ошибок может отличаться от 5% или 40%. `flaky` не означает строгое чередование успеха и ошибки.

### Переключение режимов

Выполняйте команды по одной, когда хотите изменить поведение зависимости:

```sh
./bin/scooterctl homework module-4 mode ok
./bin/scooterctl homework module-4 mode error --ttl 15m
./bin/scooterctl homework module-4 mode rare_error --ttl 15m
./bin/scooterctl homework module-4 mode slow --ttl 15m
./bin/scooterctl homework module-4 mode flaky --ttl 15m
```

Каждая команда заменяет предыдущий режим. `--ttl` ограничивает время эксперимента: после его истечения инъекция прекращается. Переключение на `ok` снимает её сразу для новых запросов. Уже начавшиеся запросы могут завершиться позже или по своему deadline.

### Что на самом деле делает команда

В k3s между Profile и Pricing работает **Envoy с фильтром fault injection**. Он обрабатывает только вызовы метода:

```text
/pricing.pricing.v1.PricingService/GetCompletedTripsCount
```

Команда `mode` меняет правила прокси: долю искусственных gRPC-ошибок либо задержку перед передачей запроса. Поддержка задержек и выборочных отказов описана в [документации Envoy](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/fault_filter); для ошибки используется именно [`grpc_status`](https://www.envoyproxy.io/docs/envoy/latest/api-v3/extensions/filters/http/fault/v3/fault.proto), а не подмена HTTP-кода.

Переключение режима не требует изменения кода сервисов или перезапуска Profile. Его circuit breaker сохраняет накопленное состояние. Прокси остаётся в маршруте и в режиме `ok`; собственные ретраи прокси не участвуют в эксперименте.

Мы воспроизводим **наблюдаемое поведение зависимости**. Сам Pricing при этом может быть здоров: инъекция ошибки завершает запрос до его обработчика. Поэтому отсутствие записи в логах Pricing ещё не означает, что Profile не сделал попытку. Сопоставляйте логи клиента и прокси.

Сетевые потери — отдельный тип эксперимента. Например, [Chaos Mesh NetworkChaos](https://chaos-mesh.org/docs/simulate-network-chaos-on-kubernetes/) умеет добавлять задержки, потери пакетов и разрывы связности. Но потеря 5% пакетов не означает ошибку 5% gRPC-вызовов: несколько RPC используют одно HTTP/2-соединение, а TCP повторно передаёт потерянные данные.

## 🔁 Генератор нагрузки

Цель генератора — создать **стабильный поток запросов**, на фоне которого видны рост latency, ошибки, срабатывание timeout, переходы circuit breaker и работа fallback.

Запустите в отдельном терминале:

```sh
./bin/scooterctl homework module-4 load --rps 2 --duration 10m --timeout 3s
```

Под капотом используется [gRPC Framer](https://github.com/ozontech/framer) с подготовленными патронами. Установку генератора, выбор адреса и подготовку запросов берёт на себя `scooterctl`.

- Запросы идут через API Gateway в `Profile.GetDiscount`.
- Нагрузка — **2 запроса в секунду**, примерно один каждые 500 мс.
- Запросы распределены между тремя учебными пользователями.
- Следующая отправка не ждёт окончания предыдущего запроса.
- У каждого запроса deadline **3 секунды**.
- Генератор не повторяет неуспешные пользовательские запросы автоматически.

В отчёте смотрите фактический RPS, число отправленных и завершённых запросов, gRPC-коды, p95/p99 и число ответов дольше 300 мс. Не исключайте таймауты и неуспешные запросы из оценки поведения системы.

Для просмотра тела отдельного ответа используйте контрольный запрос:

```sh
./bin/scooterctl homework module-4 request --user regular --timeout 3s
```

Проверяйте `discount_percent`, `degraded` и `source`. В `--user` можно передать учебное имя или явный UUID; это пригодится для проверки неизвестного пользователя и некорректного идентификатора. Контрольные запросы — дополнительный трафик: выполняйте их отдельно от итогового прогона либо учитывайте в своих подсчётах.

Генератор видит пользовательские запросы. **Сколько попыток Profile сделал в Pricing**, выясняйте по логам исходящего клиента и прокси. После добавления retry эти числа могут существенно отличаться.

## 🔹 Задание 1 — Найти альтернативный путь при отказе Pricing

> 💬 **Поддержка:** «Из-за ошибки расчёта скидки пользователь вообще не может открыть нужный раздел. Можно хотя бы показать, что скидка сейчас недоступна?»

Вам предстоит проанализировать поведение системы, когда часть её зависимостей перестаёт работать, и реализовать **fallback в Profile**.

Подумайте:

- В каких случаях допустима деградация?
- Почему `0%` с `degraded=true` отличается от подтверждённых `0%`?
- Какие ошибки нельзя превращать в успешный ответ?
- Как разработчики узнают о проблеме, если снаружи почти все запросы снова успешны?

### Проверьте своё решение

1. В `ok` запросите скидку каждого пользователя. Ожидаются 0%, 10% и 20% без деградации.
2. Переключите режим на `error` и повторите запросы. Существующие пользователи должны получить согласованный fallback.
3. Проверьте некорректный UUID и UUID отсутствующего пользователя. Fallback не должен скрывать эти ошибки.
4. Верните `ok`. Должен снова работать расчёт по истории поездок.

Затем запустите генератор и посмотрите на всю последовательность: исправная зависимость → отказ → восстановление. Сохраните несколько ответов и соответствующие записи логов.

### Вопрос на засыпку

**Какой ещё архитектурный подход к fallback подошёл бы этому сценарию?**

Например, можно ли показывать последнюю успешно рассчитанную скидку? Где хранить такое значение, как ограничить его возраст и что возвращать при первом запросе? Что изменится после перезапуска pod? Как не перепутать кэш разных пользователей?

Опишите плюсы и минусы выбранного варианта. Реализовать кэш необязательно. Также подумайте, когда пригодится feature flag, временно отключающий обращения за скидкой, и чем он отличается от автоматического CB.

## 🔹 Задание 2 — Понимание принципов circuit breaker

> 💬 **Коллега на ревью:** «Мы включили circuit breaker, но он слишком часто открывается. Может, просто отключим его?»

Прежде чем добавлять защиту, разберитесь, за что отвечает каждый её параметр. Возьмите [gobreaker](https://github.com/sony/gobreaker) или библиотеку, которую используете в своём решении, и найдите ответы в реализации. Укажите её версию.

### ❓ Вопрос 1

**Что определяет, насколько быстро CB откроется при постоянных ошибках?**

Сравните порог последовательных ошибок и долю ошибок за окно. Как на результат влияют интенсивность трафика и минимальное число наблюдений?

### ❓ Вопрос 2

**При каких настройках CB начнёт открываться даже в `rare_error`?**

Нужно ли открывать его при 5% ошибок? Почему одна ошибка из двух запросов — слабое основание для вывода о состоянии сервиса?

### ❓ Вопрос 3

**Какой параметр задаёт время нахождения в `OPEN`?**

Чем этот timeout отличается от таймаута одного RPC? Что происходит с пользовательскими запросами, пока новые обращения к Pricing запрещены?

### ❓ Вопрос 4

**Как устроен `HALF-OPEN`?**

Сколько пробных запросов допускается? Что произойдёт при их успехе и при ошибке? Кто запускает проверку восстановления: отдельная горутина или очередной пользовательский запрос?

### ❓ Вопрос 5

**Что влияет на скорость восстановления при `slow → ok`?**

Почему после снятия инъекции fallback может какое-то время сохраняться? Как интервал `OPEN`, число проб и частота входящих запросов влияют на этот период?

### ❓ Вопрос 6

**Какие побочные эффекты дают слишком маленькие и слишком большие таймауты?**

Отдельно рассмотрите время ожидания RPC и время нахождения CB в `OPEN`.

### ❓ Вопрос 7

**Почему границу CB полезно выбирать по зависимости и методу?**

Нужно ли из-за отказов `Pricing.GetCompletedTripsCount` запрещать вызовы здорового `Pricing.ListTariffs`? В каких случаях общий CB всё же оправдан?

### ❓ Вопрос 8

**Генератор делает 2 запроса в секунду. На сколько запросов ориентируется CB при `interval = 20s` и сколько приходится на бакет при `bucket_period = 10s`?**

Сначала посчитайте для одной реплики, состояния `CLOSED`, без retry и при одном обращении к Pricing на пользовательский запрос. Затем объясните, почему реальные счётчики изменятся при нескольких репликах, открытии CB и повторных попытках.

### ❓ Вопрос 9

**Зачем circuit breaker нужны поколения состояния?**

Представьте: медленный запрос начался в `CLOSED`, CB уже успел открыться и перейти к новой проверке, а старый запрос только сейчас завершился. Должен ли его результат влиять на новое поколение? Найдите соответствующую проверку в коде библиотеки.

## 🔹 Задание 3 — Защита проблемной зависимости

> 💬 **Дежурный:** «Pricing уже отвечает ошибками, но Profile продолжает обращаться к нему на каждый запрос. Личный кабинет спасли fallback'ом, а зависимость всё ещё получает бесполезную нагрузку».

### Ваша задача

Реализовать в исходящем клиенте Profile механизм, который:

- распознаёт нестабильность `Pricing.GetCompletedTripsCount`;
- временно прекращает новые обращения к этому методу;
- допускает ограниченные проверки восстановления;
- автоматически возвращается к обычной работе.

Это и есть **circuit breaker**. Не создавайте его заново для каждого запроса: он должен накапливать статистику между вызовами. Защита относится к исходящему обращению Profile, а fallback — к сценарию получения скидки. API Gateway остаётся транспортным прокси.

Разделяйте реальную ошибку RPC и локальный отказ CB пропустить запрос. Успешный fallback не означает, что Pricing восстановился, и не должен превращаться в успех в статистике его CB.

### Проверьте своё решение

Запустите генератор. Не останавливая его и не перезапуская Profile, последовательно исследуйте:

- `ok → error → ok`;
- `ok → rare_error → ok`;
- `ok → flaky → ok`;
- `ok → slow → ok`.

Между экспериментами дождитесь нормальной работы и объясните, как очистилась статистика предыдущего периода. В каждом негативном режиме наблюдайте систему достаточно долго, чтобы увидеть открытие CB, проверки и восстановление, если выбранные пороги предполагают такие переходы.

Во время прогона изучайте:

| Где смотреть | Что важно увидеть |
| --- | --- |
| Генератор | Время запроса, gRPC-код, latency, долю ответов дольше 300 мс |
| Контрольный запрос и логи Profile | Скидку, признак деградации и причину fallback |
| Исходящий клиент Profile | Допущенные RPC, ошибки, переходы CB, время и причину каждого перехода |
| Прокси | Реально поступившие попытки и результат инъекции |
| Pricing | Запросы, которые дошли до обработчика |

Приложите хронологию хотя бы одного полного цикла `CLOSED → OPEN → HALF-OPEN → CLOSED` и неуспешной проверки, вернувшей CB в `OPEN`.

При открытом CB новые обычные вызовы Pricing прекращаются. Уже начатые вызовы могут завершаться, а в `HALF-OPEN` допускаются пробы — учитывайте это при анализе логов.

**Вопрос:** если в `slow` вызовы всё-таки успешно завершаются, обязан ли CB, считающий только ошибки, открыться? Какая защита ограничивает время самого первого медленного запроса?

## 🔹 Задание 4 — Ограничение времени ожидания Pricing

> 💬 **Поддержка:** «Ошибок стало меньше, но скидка иногда загружается почти три секунды. Для пользователя это всё ещё выглядит как зависание».

После предыдущих частей вы могли заметить: наличие CB и fallback само по себе не гарантирует соблюдение SLO.

Особенно это заметно в `slow`. Пока CB ещё закрыт или пропустил пробный запрос, Profile продолжает ждать зависимость. Хотя с точки зрения бизнеса уже можно вернуть деградированный ответ.

### Ваша задача

Ограничить время ожидания `Pricing.GetCompletedTripsCount` так, чтобы:

- `GetDiscount` укладывался в SLO 300 мс;
- Profile быстро прекращал ожидание медленной зависимости;
- оставалось время на fallback и передачу ответа клиенту;
- исходящий вызов учитывал более короткий deadline входящего запроса;
- отмена запроса прекращала ненужную работу, включая ожидание повторной попытки.

Изучите конфигурацию Profile и место создания исходящего gRPC-клиента. Добавьте или настройте отдельный timeout обращения к Pricing. Параметр `grpc_server.timeout` относится к keepalive сервера и не задаёт срок выполнения бизнес-запроса.

Обоснуйте выбранное значение наблюдаемой latency в `ok`. Учтите чтение собственной БД Profile, работу gateway, сетевые задержки и подготовку ответа. Отдать downstream все 300 мс — значит не оставить времени остальным участникам.

Контекст исходящего вызова должен происходить от контекста входящего запроса. В gRPC Go это позволяет передать оставшийся deadline следующему участнику цепочки. Подробнее — в [документации по deadline propagation](https://grpc.io/docs/guides/deadlines/).

### Проверьте своё решение

Повторите `ok → slow → ok` и сравните до/после:

- время ответа Profile и p99 на генераторе;
- частоту технических ошибок и fallback;
- поведение CB;
- время восстановления нормальной скидки.

### Вопрос на засыпку

Проведите отдельный диагностический эксперимент: временно разрешите Profile ждать Pricing до **5 секунд**, оставьте deadline клиента **3 секунды** и дождитесь большой задержки в `slow`. CB не должен скрыть исследуемый вызов — для этого прогона временно отключите его. После эксперимента верните рабочие настройки.

Проследите цепочку `клиент → gateway → Profile → прокси → Pricing`:

1. Какую ошибку получает клиент по истечении своих 3 секунд?
2. Что показывает `ctx.Err()` в обработчике Profile и что возвращает его gRPC-клиент?
3. Был ли запрос вообще передан в Pricing, если задержка внесена перед отправкой upstream?
4. Если Pricing уже начал работу, как он узнаёт об отмене и прекращает её?
5. Почему нельзя считать `context.Canceled`, gRPC `Canceled` и `DeadlineExceeded` одной и той же причиной сбоя?
6. Должен ли CB учитывать отмену пользователем как отказ Pricing? А превышение локального бюджета ожидания зависимости?

Сопоставьте коды с местом возникновения и временем события. Не ожидайте одного универсального кода во всех горутинах: сервер и клиент наблюдают разные стороны отмены. Когда исходный запрос уже отменён, успешный fallback может быть некому доставлять.

**Дополнительный вопрос:** что изменится, если пользователь приходит в gateway по HTTP? Передаётся ли выбранный вами HTTP-заголовок с deadline автоматически? Где нужно проверить его значение и создать ограниченный контекст?

## 🔹 Задание 5 — Повторить запрос и не добить зависимость

> 💬 **Коллега:** «В `rare_error` всего 5% ошибок. Давайте повторять запрос, и почти все пользователи получат настоящую скидку».
>
> 💬 **Дежурный:** «Добавили повторы. Теперь при сбое Pricing обращений к нему стало больше, хотя пользователей столько же».

Retry действительно может помочь при кратковременном сбое. Но у него две цены: **время пользователя** и **дополнительная нагрузка на зависимость**.

### Ваша задача

Добавить ограниченные повторы чтения `Pricing.GetCompletedTripsCount` на стороне Profile:

1. Не более **двух попыток всего**, включая первоначальную.
2. Повтор разрешён только для выбранных технических ошибок. `InvalidArgument`, `NotFound` и отмена исходного запроса не повторяются.
3. Все попытки и паузы между ними укладываются в общий бюджет обращения к Pricing. На retry бюджет не начинается заново.
4. Между попытками есть ограниченная задержка с jitter. Она прерывается при отмене контекста.
5. Действует **общий retry budget** для этого клиента и метода, а не отдельный бюджет на каждого пользователя.

Для учебного эксперимента используйте следующие условия бюджета:

| Параметр | Условие |
| --- | --- |
| Область | Один экземпляр Profile, клиент `Pricing.GetCompletedTripsCount` |
| Окно | Неперекрывающиеся интервалы по 30 секунд |
| `P` | Число первоначальных попыток, реально начатых в текущем окне |
| `R` | Число повторных попыток, реально начатых в текущем окне |
| Ограничение | В каждый момент `R ≤ floor(0.2 × P)` |

Счётчики начинают окно с нуля. При решении о retry проверка и резервирование его бюджета должны быть безопасны при конкурентных вызовах. Если бюджета не хватает — используйте fallback.

Запросы, которые CB не пропустил, не увеличивают `P` и не создают право на retry. В `HALF-OPEN` проба выполняется без повторов. Каждая разрешённая повторная попытка должна снова учитывать состояние CB.

> 📌 Лимит «не более двух попыток» защищает отдельный запрос. Retry budget ограничивает дополнительную нагрузку от всего потока. Нужны оба ограничения.

### Проверьте своё решение

1. В `rare_error` сравните долю fallback без retry и с retry. Сколько дополнительных RPC понадобилось?
2. В `flaky` покажите исчерпание retry budget и отказ от части повторов. Для отдельного измерения бюджета можно временно отключить CB; затем обязательно проверьте их совместную работу.
3. В `error` убедитесь, что CB открывается, а retry не обходит запрет на обращения.
4. В `slow` проверьте, что повтор и его пауза не выводят ответ за общий временной бюджет.
5. Верните `ok`. Новые успешные запросы должны снова получать скидку по истории.

В отчёте разделите **пользовательские запросы**, **первоначальные RPC**, **повторные RPC** и **отказы CB до отправки**. Укажите границы окон бюджета. Успешный ответ генератору не показывает, сколько работы было сделано внутри.

### Вопросы на засыпку

- При 2 RPS сколько первоначальных обращений и сколько retry допустимы за полное окно, если CB всё время закрыт?
- Почему процент ошибок в прокси и процент fallback у пользователей после retry могут отличаться?
- Какая проблема остаётся у фиксированных окон на их границе? Чем помог бы token bucket?
- Если gateway и Profile независимо разрешат по две попытки, сколько обращений в Pricing может породить один пользовательский запрос?
- Что изменится при трёх репликах Profile с отдельными бюджетами и CB?
- Должен CB видеть результат каждой RPC-попытки или результат всей операции с retry? Объясните выбранный порядок обёрток и его влияние на статистику.
- Почему возможность безопасно повторить `GetCompletedTripsCount` нельзя автоматически переносить на бронирование или списание денег? Какую роль там играет ключ идемпотентности?

Убедитесь, что повторы не включены одновременно в нескольких слоях. Проверьте настройки gRPC service config и прокси. У gRPC также существуют прозрачные транспортные повторы — их нужно отличать от вашей бизнес-политики retry: [описание механизма](https://grpc.io/docs/guides/retry/).

## ✅ Критерии успеха и сдача

Вы должны показать не только код защитных механизмов, но и их поведение на стенде.

| Проверка | Ожидаемый результат |
| --- | --- |
| `ok` | Корректные скидки 0%, 10%, 20%; нет необоснованного fallback |
| `error` | Валидный fallback, открытие CB, прекращение новых обычных вызовов зависимости |
| `rare_error` | Обоснованные пороги CB; ограниченные retry уменьшают необходимость в fallback |
| `flaky` | Контролируемая дополнительная нагрузка; соблюдаются retry budget и правила CB |
| `slow` | Ожидание ограничено; остаётся время на fallback; выполняется SLO |
| Возврат в `ok` | Автоматическое восстановление нормальных ответов через ограниченные пробы |
| Некорректный запрос / неизвестный пользователь | Бизнес-ошибка сохраняется, не маскируется деградацией |
| Ручной cordon | Выбранный pod выходит из маршрутизации без перезапуска; другая реплика обслуживает новые соединения |

📦 Приложите:

1. Изменения кода и конфигурации Profile, необходимые для fallback, CB, timeout и retry budget.
2. Ответы на вопросы с привязкой к своему коду и версии библиотеки.
3. Таблицу **режим → настройки → число запросов → p95/p99 → ошибки → fallback → первоначальные/повторные RPC**. Для CB дополните её хронологией переходов.
4. Короткий разбор: **симптом → причина → исправление → проверка → результат**.
5. Проверки отмены контекста, границ retry budget, конкурентного доступа, бизнес-ошибок и возврата из деградации. Для изменённых Go-модулей запустите `go vet ./...` и `go test -race ./...`.
