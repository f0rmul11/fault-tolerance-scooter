# 🛴 Кейс: «Скидка, которая зависела от истории поездок»

## 🎭 Контекст истории

Пользователь ScooterFlow открывает личный кабинет и видит персональную скидку:

| Завершённые поездки | Скидка |
| --- | --- |
| 0–9 | 0% |
| 10–49 | 10% |
| 50 и больше | 20% |

За скидку отвечает **Profile**. Он проверяет пользователя в своей БД и запрашивает историю у **Pricing**:

```text
API Gateway → Profile.GetDiscount → Pricing.GetCompletedTripsCount
```

Pricing считает только поездки `COMPLETED` в собственной БД. Данные поступают через Kafka, поэтому небольшая задержка обновления истории допустима. Ответ используется для отображения и не меняет стоимость поездок.

## 🚨 Что случилось

> Имя и подписка загружаются нормально, а раздел со скидкой то возвращает ошибку, то открывается несколько секунд.

Pricing стал отвечать с ошибками и задержками. Profile продолжает обращаться к нему с прежней интенсивностью — и сам нарушает SLO.

Нужно сохранить пользовательский сценарий, снять лишнюю нагрузку с проблемной зависимости и ограничить время ожидания.

## ⚠️ Бизнес-условия и SLO

**Проблема с персональной скидкой не должна ломать личный кабинет.**

При недоступной истории допустимы **0% с явной деградацией**: `degraded: true`, `source: "fallback"`. Неизвестное число поездок нельзя выдавать за ноль: `completed_trips_count` отсутствует.

При здоровом Pricing — настоящая скидка, `degraded: false`, `source: "pricing"`. Некорректный UUID, неизвестный пользователь и ошибка собственной БД остаются ошибками.

Для корректных запросов существующих пользователей:

- **клиентский p99 ≤ 300 мс**, включая API Gateway;
- **не менее 99,9% успешных ответов**; явная деградация считается успехом;
- доля деградации учитывается отдельно. Постоянный fallback при здоровой зависимости не считается решением.

## 🧰 Стенд и инструменты

Все команды — из корня ScooterFlow. Требования к окружению описаны в основном README.

```bash
make cli
./bin/scooterctl doctor
./bin/scooterctl up --timeout 15m
./bin/scooterctl access
```

Учебные данные создаются миграциями Profile и Pricing автоматически:

| Пользователь | UUID | Поездки / скидка |
| --- | --- | --- |
| Новый | `e1df4080-17ad-44ca-aeae-9d7de2419dbb` | 0 / 0% |
| Постоянный | `704137fe-93b3-4113-8e09-ed1df4d0e0ea` | 12 / 10% |
| Частый | `57172605-9d97-4245-9417-8714196b1d20` | 55 / 20% |

Это отдельная историческая выборка для домашки. У постоянного пользователя есть и незавершённые записи — они не входят в счётчик. Во время измерений не создавайте новые поездки этим пользователям.

**Контрольные запросы:**

```bash
curl -sS http://localhost:18080/v1/profiles/e1df4080-17ad-44ca-aeae-9d7de2419dbb/discount
curl -sS http://localhost:18080/v1/profiles/704137fe-93b3-4113-8e09-ed1df4d0e0ea/discount
curl -sS http://localhost:18080/v1/profiles/57172605-9d97-4245-9417-8714196b1d20/discount
```

**Ошибки зависимости** — сравните 5%, 40% и полный отказ:

```bash
./bin/scooterctl fault profile pricing --method GetCompletedTripsCount --unavailable --percent 5 --duration 15m
./bin/scooterctl fault profile pricing --method GetCompletedTripsCount --unavailable --percent 40 --duration 15m
./bin/scooterctl fault profile pricing --method GetCompletedTripsCount --unavailable --percent 100 --duration 15m
```

**Задержка зависимости:**

```bash
./bin/scooterctl fault profile pricing --method GetCompletedTripsCount --slowdown 2s --percent 100 --duration 15m
```

Запускайте один сбой за раз в отдельном терминале. После `ACTIVE` можно подавать нагрузку. Ctrl+C или истечение duration снимают сбой; после аварийного завершения доступен `./bin/scooterctl fault profile pricing --clear`.

Процент — вероятность для каждой попытки. Инъекция действует в Envoy **до обработчика Pricing**, только на `GetCompletedTripsCount`. Перезапуск Profile не нужен; остальные методы не затрагиваются.

**Нагрузка через API Gateway:** эксперименты проводим без ретраев.

```bash
./bin/scooterctl load --addr 127.0.0.1:19090 \
  --method api_gateway.profile.v1.ProfileService/GetDiscount \
  --data '{"user_id":"704137fe-93b3-4113-8e09-ed1df4d0e0ea"}' \
  --rps 2 --duration 10m --request-timeout 3s --clients 1
```

Для исследования можно сократить duration до `1m`. Итоговые прогоны — по **10 минут** без сбоя, при полном отказе и при задержке 2s. Генератор не делает повторов; результаты сохраняет в `summary.json`: число запросов, ошибки, p95/p99. Тела ответов проверяйте контрольными запросами вне итогового прогона.

**Логи** — в отдельных терминалах:

```bash
./bin/scooterctl logs profile -f --tail 0
./bin/scooterctl logs profile --outgoing -f --tail 0
```

Во втором потоке смотрите `from: "profile"`, `to: "pricing"`: это попытки, дошедшие до прокси, включая искусственные отказы.

**После правок Profile:**

```bash
./bin/scooterctl build profile
./bin/scooterctl deploy profile --timeout 5m
./bin/scooterctl kubectl -n scooterflow get pods -l app.kubernetes.io/name=profile
```

Перед измерением дождитесь одной готовой реплики без старых `Terminating` pod и проверьте штатный ответ скидки. Перезапуск обнуляет состояние и метрики процесса. Если меняли порты, используйте адреса из `access`.

## 🔹 Задание 3 — Защита Pricing

> Личный кабинет уже работает при сбоях. Но Pricing по-прежнему получает запрос на каждое обращение пользователя — даже когда почти все попытки бесполезны.

## 🔹 Задание 5 — Наблюдаемость

После инцидента нужно понять, что происходило, даже если клиенты получали успешные ответы.

Выберите и экспортируйте базовые метрики по **`/metrics` на admin-порту Profile**. Prometheus и Grafana разворачивать не нужно:

```bash
curl -sS http://localhost:18082/metrics
```

Тот же адрес можно открыть в браузере. Формат — Prometheus text exposition.

**❓ На какие вопросы должны отвечать метрики?**

1. Сколько запросов на получение скидки пришло в Profile? Сколько завершилось штатным ответом, ошибкой или деградацией?
2. Какую долю составляют деградированные ответы? Как отличить доступный API от работающего персонального расчёта?
3. Сколько попыток действительно ушло в Pricing, а сколько обращений отсёк CB? Уменьшилась ли нагрузка на зависимость после открытия цепи?
4. В каком состоянии находится CB? Как часто и между какими состояниями он переключается? Нет ли слишком частых открытий?
5. Сколько вызовов закончилось по таймауту зависимости, а сколько — из-за отмены входящего запроса? Можно ли различить эти причины?
6. Как меняется время ответа при здоровом Pricing, ошибках и задержках? Видно ли, что ответы выходят за целевые 300 мс?
7. Сколько обращений к Pricing выполняется прямо сейчас? Остаётся ли активная работа после завершения или отмены пользовательских запросов?

Названия метрик и метки выберите сами. Не используйте UUID пользователей и request ID в качестве меток.

**Результат:**

- метрики позволяют ответить на вопросы выше и согласуются с нагрузкой и логами;
- штатный расчёт, fallback и ошибка различимы;
- сокращение исходящих попыток при открытом CB видно отдельно от числа пользовательских запросов;
- после завершения запросов активная работа возвращается к исходному уровню.

Сравните значения до сбоя, во время него и после восстановления. При сравнении учитывайте обнуление счётчиков после перезапуска процесса.
