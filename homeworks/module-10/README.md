# 🛴 Модуль 10. Кейс: «Скидка под нагрузкой»

## 🎭 Контекст

Компания **ScooterFlow** развивает сервис аренды самокатов. В личном кабинете пользователь видит персональную скидку: **0%** за 0–9 завершённых поездок, **10%** за 10–49 и **20%** за 50 и больше.

Продолжаем историю из [модуля 4](../module-4/README.md). `Profile.GetDiscount` получает количество завершённых поездок через `Pricing.GetCompletedTripsCount` и рассчитывает скидку.

```text
Пользователь → API Gateway → Profile → Pricing → PostgreSQL Pricing
                               │
                               └── Valkey Cluster: кеш скидки
```

Pricing бывает медленным и периодически отвечает ошибками. Его команда пока не может ускорить чтение истории, поэтому на архитектурном комитете приняли решение:

> **Кешировать скидку в Profile и инвалидировать её через Kafka.**

В стенде уже развёрнуты **шардированный Valkey Cluster** с поддержкой CAS и Kafka. Работаем с моделью Redis Cluster, а не Sentinel. Кешируем объект по ключу `user:{UUID}:discount`: скидку, количество поездок, настройку уведомлений, версии данных и сведения о свежести. Фигурные скобки вокруг UUID сохраняются — это hash tag пользователя.

Скидка в этом задании служит для отображения в личном кабинете. Подписка пользователя и сохранённая стоимость поездок остаются отдельными данными.

### 🎯 Бизнес-требование

Получение скидки должно быть быстрым и стабильным, даже когда Pricing работает плохо. Используйте ограничения времени и fallback из модуля 4. Устаревшие данные и fallback должны быть явно обозначены; ошибку зависимости нельзя кешировать как подтверждённую скидку 0%.

## 🧰 Подготовка и инструменты

Поднимите стенд по [основному README](../../README.md), затем выполните из корня репозитория:

```sh
./bin/scooterctl homework module-10 prepare
./bin/scooterctl homework module-10 status
```

`prepare` готовит данные и патроны. Для опытов доступны `regular` с 12 поездками, `threshold` с 9 и набор `many` из 1000 пользователей. Утилита сама подставляет UUID.

### Режимы сбоев

| Режим | Что делает команда |
| --- | --- |
| `ok` | Снимает искусственные сбои |
| `slow` | Добавляет 250 мс перед каждым вызовом `Profile → Pricing.GetCompletedTripsCount` |
| `rare_error` / `flaky` / `error` | Возвращает gRPC `Unavailable` для 5% / 40% / 100% попыток этого RPC |
| `kafka_unavailable` | Разрывает связь Profile с Kafka; Rental и Pricing продолжают обмениваться событиями |
| `cache_unavailable` | Разрывает связь Profile со всеми узлами кеша |

Задержки и gRPC-ошибки вносит **Envoy**, сетевые разрывы — **Chaos Mesh**. Команда меняет поведение на границе компонентов без изменения их бизнес-кода. Вероятность ошибки относится к каждой RPC-попытке, включая retry.

```sh
./bin/scooterctl homework module-10 mode slow --ttl 10m
./bin/scooterctl homework module-10 mode ok
```

Режимы включаются по одному. `--ttl` ограничивает длительность сбоя: после её истечения связь восстанавливается автоматически. Это не TTL кеша.

### Нагрузка

```sh
./bin/scooterctl homework module-10 load --pattern single --user regular --rps 100 --duration 1m --timeout 3s
```

Внутри scooterctl работает [gRPC Framer](https://github.com/ozontech/framer): утилита готовит патроны, запускает запросы через API Gateway и сохраняет отчёт. Самостоятельно устанавливать генератор не нужно.

Патроны: `single` — один пользователь; `uniform` — равномерно по набору `many`; `hot-key` — 90% запросов к `regular`, остальные по `many`. Генератор не делает retry. Внешний timeout 3 секунды не заменяет бюджет времени приложения.

Сравнивайте результаты до и после изменений на одинаковой нагрузке. Если компьютер не выдерживает указанный RPS даже в `ok`, уменьшите его и зафиксируйте значение в отчёте.

## 1️⃣ «После промаха кеша Pricing завалило запросами»

> 💬 **Поддержка:** «Скидка обычно появляется сразу. Но иногда личный кабинет одновременно начинает тормозить у многих пользователей. Через некоторое время всё проходит».

Команда обнаружила два случая: множество запросов к одному отсутствующему ключу и одновременное истечение TTL у разных пользователей.

### Ваша задача

- При попадании в кеш возвращать допустимое значение без обращения в Pricing. При промахе — получать данные, рассчитывать скидку и безопасно заполнять кеш.
- Объединять одновременные загрузки одного ключа через **singleflight**.
- Защитить Pricing от лавины промахов разных ключей: добавить **TTL jitter** и ограничить суммарное число параллельных загрузок.

### Проверьте

Включите `slow`, удалите ключ и запустите нагрузку `single`:

```sh
./bin/scooterctl homework module-10 cache evict --user regular
```

Затем верните `ok` и повторите опыт с разными ключами:

```sh
./bin/scooterctl homework module-10 cache warm --dataset many
./bin/scooterctl homework module-10 cache expire-together --dataset many --after 30s
./bin/scooterctl homework module-10 load --pattern uniform --rps 100 --duration 1m --timeout 3s
```

`warm` прогревает кеш обычными запросами, `expire-together` выставляет одинаковое время истечения существующим ключам. Этот искусственный удар проверяет ограничение общей нагрузки; действие jitter проверьте отдельно при естественном истечении TTL.

## 2️⃣ «Десятая поездка есть, скидки нет»

> 💬 **Поддержка:** «У пользователя завершилась десятая поездка. В истории она уже есть, а в личном кабинете всё ещё 0%. Обновление страницы не помогает».

### Ваша задача

Реализуйте событийную инвалидацию:

1. Rental публикует событие завершения поездки.
2. Pricing сохраняет изменение статистики и событие инвалидации в outbox **одной транзакцией своей БД**.
3. Relay отправляет событие в `user-discount-invalidate.v1` с UUID пользователя и `stats_version`.
4. Profile инвалидирует или актуализирует объект кеша. Повторные и устаревшие события не должны откатывать данные.

Используйте механизм outbox из стенда. Версия относится к статистике пользователя в Pricing, а не к отдельной поездке; чтение счётчика возвращает ту же версию из согласованного снимка.

**Kafka может быть недоступна для Profile до 10 минут.** Поэтому событийная инвалидация не отменяет TTL: выберите допустимый срок устаревания, настройте TTL и объясните решение. Если отдаёте stale, ограничьте и его максимальный возраст.

### Проверьте

Сначала прогрейте скидку `threshold`, затем завершите его десятую поездку:

```sh
./bin/scooterctl homework module-10 request --user threshold
./bin/scooterctl homework module-10 trip complete --user threshold
./bin/scooterctl homework module-10 request --user threshold
```

`trip complete` проводит поездку через обычные API и ждёт её учёта в Pricing. Для повторного опыта вне нагрузки выполните `./bin/scooterctl homework module-10 fixtures restore --user threshold`, затем повторите проверку в режиме `kafka_unavailable --ttl 10m`.

**Ответьте:** почему событие должно исходить из Pricing, а не только из Rental? Почему TTL нужен даже с Kafka? Что произойдёт при слишком маленьком TTL и при продлении TTL на каждом чтении?

## 3️⃣ «Сохранил настройку, а после поездки она сбросилась»

> 💬 **Поддержка:** «Включил уведомления о скидке — приложение подтвердило сохранение. Почти одновременно завершилась поездка. Обновляю страницу — уведомления снова выключены».

Ручка **`Profile.UpdateProfile`** меняет `discount_notifications_enabled`. Настройка сохраняется в PostgreSQL Profile, затем обновляется её копия в объекте `user:{UUID}:discount`. В этом опыте обработчик события Pricing **помечает скидку в том же объекте устаревшей**, сохраняя настройку уведомлений. Вместе с отметкой он записывает минимальную требуемую `stats_version`; признак актуальности возвращается только после загрузки подходящего снимка Pricing.

Гонка возникает между двумя путями изменения:

1. **Обработчик события на Profile A** читает объект: уведомления выключены. Он готовит инвалидацию скидки, но ещё не сохраняет её.
2. **Ручка UpdateProfile на Profile B** сохраняет включённые уведомления в БД и обновляет кеш.
3. **Обработчик события** записывает подготовленный ранее объект целиком. Вместе с инвалидацией в кеш возвращается старая настройка — «выключено».

В обратном порядке ручка может сохранить настройку, но затереть отметку инвалидации и снова объявить старую скидку актуальной. Данные в БД при этом остаются правильными.

### Ваша задача

Используйте **CAS — Check-and-Set / Compare-and-Set** в обоих путях: обработчике события и обновлении кеша из ручки.

> «Сохрани изменение, только если объект всё ещё находится в том состоянии, которое я прочитал».

Изучите [документацию Valkey SET, опцию IFEQ](https://valkey.io/commands/set/) — она доступна с **8.1.0**:

```text
SET <key> <new-object> IFEQ <previous-object> KEEPTTL
```

При конфликте перечитайте объект и **заново примените только своё изменение**: событие сохраняет актуальные настройки, ручка сохраняет актуальную отметку инвалидации. Нельзя повторять старый объект с новым ожидаемым значением. Версии профиля и статистики независимы: ни одна не должна откатываться. CAS кеша не заменяет проверку версии при записи профиля в БД.

Сравнивайте исходные байты объекта, ограничьте число попыток и сохраните TTL. Изменение настройки не продлевает свежесть скидки. Если ключ успел исчезнуть, не восстанавливайте его из устаревшего снимка.

### Проверьте

```sh
./bin/scooterctl homework module-10 replicas profile 2
./bin/scooterctl homework module-10 run cas-invalidation --user threshold --iterations 100
```

Команда запускает изменения настройки через API одновременно с поездками и доставкой событий инвалидации. Она проверяет реальные обработчики; напрямую готовые объекты в кеш не записывает. Для гарантированного воспроизведения дополните прогон тестом с барьерами после чтения кеша и настоящим Valkey.

Проверьте **обе очередности записи**, повтор события и несколько конкурентных вызовов ручки. В результате сохраняются последняя принятая версия настройки и инвалидация либо уже подтверждённая свежая скидка. Отклонённый по версии запрос не считается принятым изменением.

**Ответьте:** почему `GET → проверка → SET` недостаточно? Почему CAS только в одном из двух путей не решает проблему? Почему после конфликта нужно заново применить изменение, а не повторить подготовленный объект?

## 4️⃣ «Pricing разгрузили, а кеш стал узким местом»

> 💬 **Дежурный:** «Запросов в Pricing почти нет. Но один узел кеша загружен сильнее остальных. Добавили шард — популярный профиль быстрее не стал».

### Ваша задача

Найдите горячий ключ и уменьшите количество обращений к общему кешу — например, через небольшой **локальный L1** с ограниченным размером и TTL. Свежесть скидки должна сохраняться и при двух репликах Profile.

```sh
./bin/scooterctl homework module-10 replicas profile 2
./bin/scooterctl homework module-10 load --pattern hot-key --rps 100 --duration 1m --timeout 3s
./bin/scooterctl homework module-10 cache inspect --user regular
```

Проверьте, что запросы приходят на обе реплики. Сравните число операций общего кеша до и после L1. `cache inspect` показывает объект, TTL, слот и узел, на котором лежит ключ.

Затем включите `cache_unavailable`. Ошибка кеша не должна отправлять весь пользовательский поток в Pricing: используйте допустимое локальное значение либо fallback с ограничением обращений к источнику. После `mode ok` обычная работа должна восстановиться.

**Ответьте:** почему новый шард не делит один горячий ключ между узлами? Почему singleflight не уменьшает количество обычных cache hit? Если две реплики Profile состоят в одной Kafka consumer group, как инвалидировать оба L1 или ограничить время их устаревания?
