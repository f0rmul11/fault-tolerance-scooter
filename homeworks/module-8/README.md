# 🛴 Модуль 8. «Поездка завершилась, а стоимость так и не появилась»

## 🎭 Контекст истории

Компания **ScooterFlow** развивает сервис аренды самокатов.

Когда пользователь бронирует самокат:

1. `Rental` сохраняет аренду и событие в своей БД.
2. Outbox worker отправляет событие `rental.reserved.v1` в Kafka.
3. `Pricing` сохраняет сообщение в inbox.
4. Обработчик inbox получает подписку пользователя из Profile и фиксирует тариф поездки.

При начале и завершении поездки Rental публикует следующие события. Pricing учитывает аванс и рассчитывает итоговую стоимость.

На первый взгляд — всё просто. Но в поддержку начали приходить жалобы.

> 🎯 Ваша задача — проверить доставку событий и обработку дублей, добавить retry topic и DLQ, чтобы сбои не приводили к потере событий или остановке остальных поездок.

## 🧰 Подготовка стенда

Все команды выполняются из корня репозитория:

```sh
make cli
./bin/scooterctl up --timeout 15m
./bin/scooterctl status
./bin/scooterctl access
```

| Что открыть | Адрес и данные |
| --- | --- |
| API / Swagger | http://localhost:18080/docs/ |
| AKHQ | http://localhost:18090, подключение `scooterflow` |
| БД Rental | `127.0.0.1:25440`, база `rental`: таблицы `rentals`, `outbox` |
| БД Pricing | `127.0.0.1:25441`, база `pricing`: таблицы `trips`, `inbox` |

Учётные данные БД выводит `scooterctl access`. Основной топик — **`rental.events.v1`**, consumer group — **`pricing-rental-events`**. В базовом стенде одна партиция — `0`.

Выполните обычную поездку через Swagger: бронирование → начало → завершение → чтение стоимости. [Примеры запросов](../../docs/api.md) и [учебные пользователи и самокаты](../../docs/seed.md) помогут подготовить данные.

Для новой брони используйте новый `idempotency_key`, для повтора того же запроса — прежний. Перед новым опытом завершите поездку или отмените бронь: пользователь и самокат могут иметь только одну незавершённую аренду.

### Команды для сбоев

| Что проверяем | Остановить | Восстановить |
| --- | --- | --- |
| Доставка из outbox при отказе Kafka | `./bin/scooterctl stop kafka` | `./bin/scooterctl start kafka` |
| Приём в inbox при отказе БД Pricing | `./bin/scooterctl stop pricing-postgres` | `./bin/scooterctl start pricing-postgres` |
| Сохранение аренды при отказе БД Rental | `./bin/scooterctl stop rental-postgres` | `./bin/scooterctl start rental-postgres` |
| Ошибка обработки уже принятого события | `./bin/scooterctl stop profile` | `./bin/scooterctl start profile` |
| Остановка consumer для работы с offset | `./bin/scooterctl stop pricing` | `./bin/scooterctl start pricing` |

`stop/start` сохраняют данные. Выполняйте опыты по одному и восстанавливайте компонент перед следующим. Состояние смотрите через `scooterctl status`, сообщения — в AKHQ, результат обработки — в таблицах БД.

## 🚨 Инцидент №1 — «Аренда появилась, но Pricing её не увидел»

> 💬 **Поддержка:** «Пользователь забронировал самокат. Бронь есть в списке, а стоимость не появляется. В это время были проблемы с Kafka».

Если сначала сохранить аренду в БД, а потом отдельно отправить событие, между этими действиями может произойти сбой:

- сервис упал;
- Kafka недоступна;
- publish завершился ошибкой или timeout.

→ аренда уже в БД;
→ события нет;
→ Pricing ничего не знает.

### ⚠️ Бизнес-аксиома №1

> **Потеря события хуже, чем задержка события.**

Допустимо обработать событие позже или доставить повторно. Недопустимо его потерять.

### 🎯 Задание 1 — Гарантия доставки события

Изучите outbox в Rental. Проверьте, что состояние аренды и событие сохраняются одной транзакцией, а после восстановления Kafka отправка продолжается без нового запроса пользователя. Исправьте обнаруженные проблемы.

### 🧪 Проверка outbox

1. При работающем Rental выполните `./bin/scooterctl stop kafka`.
2. Забронируйте свободный самокат через Swagger.
3. Найдите аренду в `rentals`, а её событие — в `outbox`. У события `processed_at` должен оставаться пустым.
4. Выполните `./bin/scooterctl start kafka`.
5. Не повторяя бронирование, дождитесь события в AKHQ, заполнения `outbox.processed_at` и появления расчёта в Pricing.

**Отдельно проверьте отказ БД Rental:** остановите `rental-postgres` до нового бронирования. Запрос не должен успешно создать аренду. После запуска БД убедитесь, что не появились ни новая аренда, ни событие о ней. Это отличается от отказа Kafka: outbox помогает доставить уже сохранённое событие, но не заменяет недоступную БД.

### 🧪 Проверка inbox

1. При работающем Pricing выполните `./bin/scooterctl stop pricing-postgres`.
2. Создайте новую бронь. Убедитесь, что её событие появилось в Kafka.
3. Проверьте группу `pricing-rental-events`: это сообщение не должно быть подтверждено, пока оно не сохранено в inbox.
4. Выполните `./bin/scooterctl start pricing-postgres`.
5. Убедитесь, что сообщение попало в `inbox` и расчёт появился в `trips` без повторного бронирования.

**Теперь остановите Profile:** `./bin/scooterctl stop profile` и создайте ещё одну бронь. БД Pricing работает, поэтому событие может попасть в inbox, но обработка завершится ошибкой. Посмотрите `processed_at`, `errors_count` и `error_desc`. Верните Profile командой `./bin/scooterctl start profile` и дождитесь обработки.

**Вопрос:** почему при отказе БД Pricing растёт Kafka lag, а при отказе Profile сообщения могут накапливаться в inbox уже после подтверждения Kafka offset?

### 🧪 Проверка дублей через AKHQ

1. Найдите успешно обработанное событие начала или завершения поездки в `rental.events.v1`.
2. Откройте форму создания сообщения и отправьте его копию: **тот же key, value и все headers**.
3. Сохраните прежний `correlation_id` в теле и `x-correlation-id` в заголовке — это повтор того же события.
4. Убедитесь, что повторная доставка не изменила начисления и версию расчёта повторно.

### Вопросы для размышления

- Что будет, если Kafka приняла событие, а Rental не успел сохранить `processed_at`?
- Чем отличаются `idempotency_key`, `correlation_id` и `rental_id`?
- Почему outbox не отменяет необходимость идемпотентного consumer?
- Какие новые точки отказа появляются вместе с outbox и inbox?

## 🚨 Инцидент №2 — «Одна плохая запись остановила всю партицию»

> 💬 **Поддержка:** «Новые поездки создаются, но стоимость перестала появляться. В логах Pricing повторяется одна ошибка. Перезапуск не помогает».

В топик попало сообщение с неправильной схемой или неожиданным payload. Consumer не может его обработать и не подтверждает offset. При повторном чтении ошибка возникает снова.

> **Одна запись блокирует обработку следующих сообщений партиции.**

### 🧪 Ручное восстановление до внедрения retry и DLQ

1. В AKHQ откройте `scooterflow` → `rental.events.v1` → создание сообщения.
2. Выберите партицию `0`, задайте key новым UUID и отправьте value:

   ```json
   []
   ```

   Это корректный JSON, но неверная схема: Pricing ожидает объект. Ошибка возникнет до сохранения в inbox, ещё до проверки headers.

3. Сохраните partition и offset плохой записи. Создайте корректную бронь после неё и убедитесь, что обработка этой партиции остановилась.
4. Попробуйте сдвинуть offset группы через AKHQ при активном consumer. Зафиксируйте результат и объясните, почему для сброса offset группа должна быть неактивна.
5. Выполните `./bin/scooterctl stop pricing` и дождитесь отсутствия активных участников группы.
6. В AKHQ установите offset **только этой партиции группы `pricing-rental-events`** на `offset плохой записи + 1`.
7. Выполните `./bin/scooterctl start pricing` и убедитесь, что следующая корректная запись обработалась.

Не используйте «to latest»: можно пропустить и корректные сообщения. Ручной сдвиг — аварийный обход с пропуском записи, а не решение проблемы.

**Вопрос:** как остановить участие consumer в группе, не завершая сам pod? Почему изменения readiness для этого недостаточно?

### ⚠️ Бизнес-аксиома №2

> **Одна ошибка не должна останавливать обработку остальных поездок.**

Система должна изолировать проблемное сообщение и продолжать работу.

### 🎯 Задание 2 — Retry topic и DLQ

Организуйте обработку ошибок с тремя топиками:

| Топик | Назначение |
| --- | --- |
| `rental.events.v1` | Основной поток |
| `rental.events.v1-retry-30s` | Отложенные повторные попытки |
| `rental.events.v1-dlq` | Сообщения, автоматическая обработка которых прекращена |

Ожидаемое поведение:

1. Временная ошибка → повторная попытка через retry topic.
2. Между попытками проходит **не менее 30 секунд**.
3. После **5 неудачных попыток всего, включая первую**, сообщение попадает в DLQ.
4. Заведомо повреждённое сообщение можно сразу направить в DLQ.
5. Корректные события других аренд продолжают обрабатываться.

### ⚙️ Требования к решению

- **Одного retry topic достаточно.** Название топика не создаёт задержку: реализуйте backoff и не заставляйте основной consumer ждать 30 секунд.
- Сохраняйте исходное сообщение, key, headers, `correlation_id` при наличии, исходные topic/partition/offset, номер попытки и причину ошибки. Счётчик и срок следующей попытки должны переживать рестарт.
- Не подтверждайте исходную запись, пока её дальнейшая обработка не обеспечена: ошибку отправки в retry/DLQ нельзя превращать в потерю события.
- Согласуйте retry topic с inbox: одно событие не должно независимо повторяться двумя worker'ами. Параметр `max_err_count_for_message` сам по себе не реализует DLQ.
- Сохраняйте порядок применения версий **одной аренды**. Если её предыдущее событие задержалось, последующие не должны портить расчёт. Другие аренды при этом продолжают обрабатываться.

Retry должен помогать системе восстановиться, а не увеличивать нагрузку во время сбоя.

### 🧪 Проверка

| Сбой | Что сделать | Ожидаемый результат |
| --- | --- | --- |
| Битое сообщение | Отправить `[]` через AKHQ, затем создать корректную бронь | Плохая запись в DLQ, корректная обработана без ручного сдвига offset |
| Временная ошибка | Остановить Profile, создать бронь, после первой ошибки вернуть Profile | Событие обработано через retry без нового бронирования |
| Длительная ошибка | Оставить Profile выключенным на все 5 попыток | Есть задержки между попытками; после пятой ошибки сообщение в DLQ, шестой попытки нет |
| Перезапуск | Во время ожидания retry выполнить `./bin/scooterctl restart pricing` | Сообщение не потеряно, счётчик не обнулён, повтор не происходит раньше срока |
| Дубль | Повторно отправить обработанное событие через AKHQ | Начисления не повторяются |

Проверьте также ошибку **внутри inbox**: скопируйте корректное `rental.reserved.v1`, замените `correlation_id` и `rental_id` на новые UUID и обновите соответствующие header/key. В payload укажите `user_id: "not-a-uuid"`, остальные поля сохраните. Сообщение должно изолироваться, а не бесконечно повторяться из inbox.

Наблюдайте попытки в логах Pricing, сообщения — в трёх топиках AKHQ, состояние — в `inbox` и `trips`. **Нулевой Kafka lag ещё не означает успешный расчёт стоимости.**

После изменения кода:

```sh
./bin/scooterctl build rental pricing --timeout 10m
./bin/scooterctl deploy rental pricing --timeout 10m
```

## ✅ Критерии успеха и сдача

- [ ] После восстановления Kafka или БД событие доходит до обработки без повторного бронирования.
- [ ] Повторная доставка не приводит к повторному начислению.
- [ ] Одно плохое сообщение не блокирует корректные события других аренд.
- [ ] Retry выполняется с задержкой и ограниченным числом попыток; DLQ сохраняет сообщение и причину отказа.
- [ ] Порядок версий одной аренды не нарушает расчёт стоимости.
- [ ] Вы умеете найти проблемную партицию и объяснить последствия ручного изменения offset.

📦 Приложите изменения, ответы на вопросы и короткий отчёт: **что было → что исправили → как проверили → что получили**.

Достаточно результатов опытов, фрагментов логов и скриншотов AKHQ/таблиц. Для проблемного события покажите его ID, partition/offset, номера и время попыток.
